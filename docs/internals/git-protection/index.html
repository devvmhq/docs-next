.git protection

.git protection

This page explains what devvm locks in a project’s git folder, when it locks and checks the locks again, and what the locks can’t stop. .git protection covers what still works, turning protection on or off, strict, and what isn’t covered.

On macOS devvm locks with the user-immutable flag (chflags uchg), which even root in the VM can’t clear. A read-only mount wouldn’t hold, because root in the VM can unmount it.

On Linux devvm makes the same paths read-only in the user and mount namespace it runs the VM’s QEMU in (on Linux hosts), so the VM, which reaches the folder only through QEMU, can’t change them.

Each check reads each repo’s .git once, the folder’s own and those nested in it, finding its git folders, submodules, what it would lock, what the locked files hand over and what points git elsewhere, and then locks, unlocks, watches and reports from what it found. The host’s locker does the locking: the flag on macOS, and on Linux nothing at the check itself, because the VM’s next start makes the paths read-only. A Linux host whose kernel refuses devvm the namespace locks nothing, and devvm watches .git there instead.

What’s locked

devvm locks these paths, of the folder’s own repo and of each nested repo it protects:

  • .git/hooks and .git/config. A repo without a hooks folder gets an empty one, locked, so the VM can’t make one.
  • The same paths for each submodule devvm finds, submodules of submodules included. Those are the git folders under .git/modules, and those in the working tree, which are sub/.git or the folder that a sub/.git file points to. devvm finds the submodules from the index, which it reads with core.fsmonitor off. It takes a folder for a git folder only when it has what git looks for in one, which is a HEAD, and objects and refs in the folder or in the folder its commondir names, as git’s own test has it. The VM can point a sub/.git file at any folder in the project, such as src, and locking that folder’s hooks and config would lock your own files, so devvm locks and creates nothing in a folder that fails the check and reports it instead.
  • .git/config.worktree, when extensions.worktreeConfig is on. devvm creates it empty if it’s missing.
  • What linked worktrees elsewhere on your machine read from here, which is .git/worktrees/<name>/commondir and config.worktree.
  • The project folder’s .git file, if the project folder is itself a linked worktree. The repo it points to is outside the VM.

When devvm locks

devvm records a new VM’s mode in its state before its backend makes the VM, so the mode is never unset: on with locks (macOS, and Linux where the kernel lets devvm use a user namespace), off when you pass --no-git-protect or on hosts without locks, and clone for a --clone VM, which mounts no .git. devvm locks once the backend has made the VM, and again on each launch that finds the VM stopped and on devvm stop, so nothing in the VM can race the locks. A VM whose creation stopped before its first locks, or that devvm adopt moved to this folder, is locked on its next launch as a new VM is, without reports. A running VM keeps the locks it had, and devvm stop or the next launch that finds the VM stopped, such as devvm restart, sets new ones. devvm git-protect on a running VM saves the mode in the VM’s state (the git section’s next).

Each time it locks, devvm records in the VM’s state what it locked and found: the identity of .git (its device and inode, and its birth time where the file system keeps one), every git folder it locked besides .git (those under .git/modules and the submodules’ in the working tree, in one list), and a hash of what the locked files hand over to the project folder. The next check compares with those, so it reports what changed since. The same places first check .git under the mode the VM ran with, so a .git that the VM replaced meanwhile is still named (git_replaced), and then set the new mode, which locks .git as it is then.

A new VM that’s interrupted before its first shell is deleted, and devvm takes its locks off. When devvm rm deletes a VM, devvm also takes its locks off. It unlocks what it would lock now and every git folder the VM’s state records locking, so a submodule whose entry the VM dropped from the index since is unlocked too.

Symlinks

devvm never locks or creates anything through a symlink, because the VM could plant one under .git so that devvm would lock a file elsewhere. devvm reports a path that is a symlink, or is under one, instead of locking it (git_not_locked). devvm also checks each lock again once it’s set. If the path moved in the meantime, devvm unlocks it where it landed and reports it (git_lock_raced).

On each launch

Every launch of an existing VM, every export of its agents’ history, and devvm stop check .git again. devvm reports each of these once:

  • A .git that was replaced since devvm locked it (git_replaced). devvm then does nothing else, so check the new .git, and look for the old one, renamed.
  • A repo that appeared in the folder after the VM was made (git_appeared), which devvm then locks, and a nested repo that appeared since the last check (git_nested_appeared).
  • A nested repo devvm protected that’s gone (git_nested_gone).
  • A submodule git folder that appeared, in the working tree or under .git/modules (git_embedded_new), which devvm then locks. devvm compares with the git folders it recorded last time, so devvm git-protect on after a VM was made without protection names none: it locks .git as it is then, as trusted.
  • Hooks in a hooks folder that wasn’t locked, because it wasn’t there to lock or belongs to a new submodule (git_hooks_unlocked).

devvm also reports these, the first two on every launch and the last two when they change:

  • A commondir (git_commondir).
  • Linked worktrees whose commondir leads elsewhere (git_worktree_stray).
  • Includes and hook links into the project folder (git_include_inside, git_hook_link_inside), which not covered describes.
  • Submodules whose git folder, in the working tree, isn’t a git folder (git_gitdir_not_git), which devvm doesn’t lock.

Nested repos

devvm protects each git repo nested in the project folder as it protects the folder’s own: it locks the same paths of each, checks each at every launch, pins each on Linux and watches each where the host can’t lock (nested repos).

The walk

devvm finds the nested repos by walking the project folder when it creates the VM, at each launch that finds the VM stopped and at devvm stop, at devvm git-protect on a stopped VM, and when devvm clone off mounts the folder again. It’s one walk that also finds the set-id files on a Linux host (hostsafety.Walk, which only starter.walk calls), and a launch into a running VM never walks. The walk stays on the project folder’s file system, follows no symlink and never enters a .git folder, so it never finds the repos of .git/modules, which are the folder’s own repo’s to protect. It takes a folder for a repo when the folder has anything named .git, a folder, a file, which a linked worktree or a repo with its git folder elsewhere has, a symlink or anything else, whether git takes it for a repo’s now or not, because the VM can make it one at any time. On macOS, whose file systems fold case, .GIT is .git to git, so the walk takes any case of the name there (platform.FoldsCase). It looks for repos at most four folders below the project folder, and not in node_modules, vendor, .venv, __pycache__ or .terraform, which package managers and build tools fill with what they fetch, so on macOS, where there are no set-id files to look for, the walk doesn’t enter those folders at all. On Linux it walks them for set-id files anyway, and counts the .git it sees there and below four folders (git_nested_skipped). It counts the folders it doesn’t enter because they’re on another file system (git_nested_devices). It keeps the first 100 repos it finds, in the walk’s order, and counts the rest, keeping the names of the first ten of those (git_nested_past_bound).

The walk also names each folder up to four folders down that git could take for a bare repo (git_nested_bare), one shaped like a git folder by git’s own test (hostsafety.IsGitDir): a HEAD, and objects and refs, files or folders, in the folder or in the folder its commondir names. A git folder that a repo’s scan locks, or that a nested repo’s .git file names, isn’t named. devvm doctor reads safe.bareRepository from git’s global and system config (hostsafety.BareExplicit), the files that GIT_CONFIG_GLOBAL and GIT_CONFIG_SYSTEM name included, which it reads by name (hostgit.UserConfig) because devvm’s host git ignores every GIT_* variable, and it gives a tip unless the setting is explicit (doctor_git_bare).

A check takes the repos the walk found, the ones the VM’s state records first. A recorded repo stays protected, whether the walk found it or not, while its folder is a real folder of the project with anything at its .git, because the VM can make a .git that the walk or git’s own test passes over while git still takes it: objects and refs renamed with a commondir that leads to a git folder of its own, a .GIT, or a .git it can’t read, which devvm can’t lock and names (git_not_locked). A check without a walk, such as devvm rm and the start that pins, takes the repos the state records. A launch into a running VM checks the folder’s own repo alone and keeps the nested repos’ records as they are, because it locks nothing and the VM can change them until it stops, so it never pays for scanning them, and the check of a running VM’s pins goes by those records without scanning them. devvm scans each repo as it scans the folder’s own, eight at once, because each scan runs a few host git commands: a check of a stopped VM with 50 nested repos, the walk and the locks included, takes under a second on an M3 Max.

Two bounds

Each repo has two bounds. Its own top folder is where its .git is, where .git/modules and a relative core.hooksPath are read from, and where its submodules’ folders are. The project folder, which the VM mounts, is what the VM can write, so it’s the bound for everything else: devvm locks only a real path in the project folder, through no symlink, an include or a hooks path leads inside when it leads into the project folder, and a submodule’s git folder outside the project folder is one devvm can’t lock (git_gitdir_outside). A nested repo’s hooks path that leads into a sibling repo is inside, because the VM can write it.

A nested repo is left to another repo only when that repo’s scan locks its git folder whole (snapshot.covered): the git folder is that repo’s .git, one under its .git/modules that reads its config from itself, with no commondir that leads elsewhere, or one of its linked worktrees under .git/worktrees whose commondir leads back. Anything else below a .git, such as a .git/evil the VM made for a src/.git file to name, isn’t locked by anything, so the repo is scanned on its own, and named as one that appeared and as one devvm doesn’t protect. A submodule in the working tree is scanned as a repo of its own as well as its parent’s submodule, because the index that names it is the VM’s to write: a gitlink the VM adds, whose .git file names a nested repo’s git folder, would otherwise hide that repo’s own submodules and worktrees behind a scan from the wrong folder. Locking a path twice changes nothing, and unlocking goes by path once. A nested repo whose .git is a file is locked as the folder’s own is when it’s a linked worktree, by its .git file. When the git folder that file names is in the project folder and no repo’s scan locks it, devvm names the repo as one it doesn’t protect, and when it’s outside the project folder, it names the repo as one whose git folder it can’t lock (git_nested_gitdir_outside), as it does a submodule’s.

A scan follows each submodule git folder once, by its resolved path, and one check’s scans follow at most 1,000 of them across every repo, so gitlinks that the VM points back at a git folder already followed, or through a symlinked folder at the repo itself, or many repos full of submodules, can’t make a check run git without end. A repo whose scan stopped there is named at every check (git_scan_bounded).

What’s recorded

The VM’s state records each protected nested repo in the git section’s made.repos, by its folder relative to the project folder, with the same fields as the folder’s own repo: .git’s identity, the git folders locked besides .git, and a hash of what its locked files hand over. made.nested is set once the VM protects its nested repos, which a new VM does, and so do devvm git-protect on and strict, and the watch on a Linux host that can’t lock. A nested repo without a record is scanned for the first time, which records it as a new VM’s repo is recorded, without reporting its git folders. At a check of a VM whose made.nested is set, devvm also reports it as one that appeared, such as a repo the VM cloned while it ran, naming each key of its config that runs a program or reads another config (core.fsmonitor, core.hooksPath, core.sshCommand, core.pager, filters, aliases that start with !, includes and the like) and each hook that isn’t one of git’s samples (git_nested_appeared_runs, else git_nested_appeared), because it locks the repo as it is. A recorded repo with nothing at its .git, or whose folder isn’t a real folder of the project any more, is reported (git_nested_gone), and a recorded repo whose .git is another one is reported as the folder’s own is (git_replaced). The record of a repo devvm stops protecting, as it’s gone or another repo’s protection covers it, moves to made.left, so devvm rm and devvm git-protect off take its locks off with the rest, and name one that isn’t in the folder any more (git_locks_left), whose locks only chflags can take off.

A VM an earlier devvm made has no made.nested, so it protects only the folder’s own repo. The first check of it that finds nested repos names them once (git_nested_protectable, recorded as nested_noticed), and devvm git-protect on protects them. The nested repos that a check finds and the protection doesn’t cover are recorded in nested, with nested_more for how many more the walk counted, and named (git_nested_unprotected, git_nested_past_bound): on a host that locks, all of them when devvm creates the VM and at devvm git-protect on or strict, and at a check of a stopped VM those it hadn’t recorded, and how many are past the bound at every check, because the VM could keep their count and change which they are. On a Linux host that can’t lock, each launch names those the last walk recorded, after git_unprotected, which a folder without a .git of its own gets too when it has nested repos, and devvm git-protect off quiets both.

Strict sets diff.ignoreSubmodules = all in the config of each protected repo that has a .git folder, and devvm git-protect on and off take it out of each.

Two VMs, one repo

A nested repo with a VM of its own is protected by two VMs, the parent folder’s and its own. On macOS both set the same flag on the same files, so when one VM’s protection comes off, at devvm rm or devvm git-protect off, devvm leaves locked every path that another VM’s protection still covers (gitprotect.Keeps: a git folder it recorded locking, of its own repo or of a nested one), and names that VM (git_kept_locked). The inventory reads every VM’s state for that (Inventory.GitKeeper). It fails closed: a state it can’t read keeps locked every path in the folder whose hash names that state’s folder (project.Hash), and when it can’t read the VMs’ folder at all, everything stays locked, each named with the state to fix (git_kept_unread). Locking a VM’s repos and recording them, and unlocking another’s, take the host’s lock of .git protection first (paths.Dirs.GitLock, before any VM’s own lock), so one VM’s unlock never runs between another’s locks and their record. devvm git-protect strict, on and off never unlock a config another VM keeps locked to set or take out diff.ignoreSubmodules, because that VM, running, could race the unlocked file, and they name that VM instead. When setting it fails, devvm locks again each config it unlocked that was locked before. On Linux each VM’s pins are in its own QEMU’s namespace, and the watch locks nothing, so neither needs this.

On Linux hosts

Linux hosts have no immutable flag that a user can set, so devvm makes what it locks read-only where the VM sees it, in the VM’s QEMU process, which serves the project folder to the guest over 9p. Lima starts QEMU through devvm’s wrapper (devvm _qemu exec), and a start of a VM that’s on or strict gives the wrapper what to pin in a file of its own, run/git-pins.json in the VM’s folder, written private, which DEVVM_QEMU_PINS names, because a VM with many nested repos has more pins than one environment variable holds. The wrapper reads the file through no symlink, and it pins, for the folder’s own repo and each nested repo the VM’s state records protecting, .git and each git folder it locks besides, which stay writable, and every path of what’s locked that’s there, which become read-only. They’re the paths the check before the start found and checked, each a real path in the project folder with no symlink, and the check made a missing hooks folder and config.worktree first, so each has a place to pin. devvm then starts devvm _qemu pinned in a user and mount namespace of its own, as you, with only CAP_SYS_ADMIN, and only in that namespace. It makes the namespace’s mounts private, so nothing it mounts reaches this machine’s, and pins each path in order, a folder before what’s under it. It opens each path once, by the kernel, below the project folder and through no symlink (openat2 with RESOLVE_BENEATH and RESOLVE_NO_SYMLINKS), refuses anything but a file or a folder, and refuses a file with another name, or a folder holding a regular file with one, because a bind covers one name and macOS’s flag covers the file itself (git_pin_linked, which the check before the start names first). Then it binds what it opened over itself with open_tree, mount_setattr and move_mount, which act on that file descriptor and never on a path again, because mount(2) would follow a symlink that the VM planted. A path it can’t pin, or folders it can’t watch, stop the start (qemu_pins_failed), so the VM never runs unlocked. Then it starts devvm _qemu drop as its child, which clears every capability it has, ambient, permitted, effective and inheritable, sets no-new-privileges and replaces itself with QEMU, which runs as you with no capability at all. Its bounding set stays whole, which only CAP_SETPCAP could change, and gives nothing with no new privileges. QEMU is killed if devvm _qemu pinned ends (PR_SET_PDEATHSIG), which runs as long as QEMU does, keeping the pins, so QEMU never outlives what keeps them. devvm _qemu exec waits for both and passes them the signals Lima sends, and if it’s killed, QEMU is killed with it, an unclean stop for the guest, as if its power went.

The guest reaches the project folder only through QEMU, so a write to a pinned path gets EROFS, and a rename or a removal of one, .git itself included, gets EBUSY, because it’s a mount point. A mount can’t be undone from the guest, and QEMU, which has no capability, can’t undo it either. A bind mount over a folder is a file system of its own to the guest, so a rename between the working tree and .git gets EXDEV. The namespace ends with QEMU, so nothing persists once the VM stops, and nothing changes on this machine’s side, where git works as usual.

A git command on this machine that writes .git/config writes a new file and renames it over the old one, and the new file isn’t pinned in the namespace. devvm _qemu pinned watches each pinned path’s folder with inotify, a few folders for each repo, so the 100 nested repos devvm protects at most stay far below the kernel’s limit of watches, and it pins again whatever lost its pin as soon as one changes, and every two seconds besides. Until then the guest can write the new file, rename it away and put its own in its place, which then gets the pin, open it for writing, a handle the pin doesn’t take back, or give it another name. So each pin it makes again, and each it can’t, it records in the VM’s run folder (run/git-pins.jsonl), a JSON object a line, after a first line that says it keeps the pins from then on, which it writes before QEMU starts and without which QEMU doesn’t start (qemu_pins_failed). The next check of the stopped VM, at devvm stop or at the next launch, names them before anything else, one line for each path and kind however often it happened (git_pin_again, git_pin_linked_run, git_pin_lost), then removes the file. An event devvm _qemu pinned can’t add goes to Lima’s log, with a warning, and to the file as a mark if it still takes one. A record the check can’t trust is named (git_pins_unrecorded): one it can’t read, which it keeps, a line that isn’t an event, a mark, or a file that doesn’t start with a run’s first line, as when it was removed while the VM ran and made again. The check also sums what a lock covers, as the watch does, and names what changed since the VM’s last check, so a file the guest changed in that window, or through a handle it kept, is named too. macOS’s flag has no window, because a locked config can’t be replaced on the host either.

Each launch of a running VM that’s on, and devvm stop before it stops it, read QEMU’s mounts (/proc/<pid>/mountinfo, QEMU’s pid from Lima’s qemu.pid) and name what of .git and of the git folders it locked QEMU lacks (git_pins_missing): .git and each git folder that isn’t a mount point of its own, and each read-only path that QEMU doesn’t see read-only,, such as all of them for a VM that limactl start started. A VM that’s on whose .git has nothing devvm can pin, such as one whose .git is a symlink, is named at its start (git_pins_none).

devvm checks that the host can pin by doing it: it pins a file in a namespace of its own, with its own binary, and checks that writing it fails (devvm _qemu probe). Lima’s read-only-paths feature is native where that works and none elsewhere, and a VM that’s on needs it to start, so where the kernel stops letting devvm in, the start is refused (backend_lacks) and never goes on unlocked. Where the probe fails, new VMs get off, devvm watches .git instead, and devvm doctor says why: Ubuntu’s kernel.apparmor_restrict_unprivileged_userns, kernel.unprivileged_userns_clone or user.max_user_namespaces at 0, or the probe’s own error. devvm offers no AppArmor profile for Ubuntu, because a profile for a binary in a folder you can write gives any program running as you what Ubuntu’s restriction holds back (Ubuntu). devvm makes the namespace itself rather than through unshare(1), so the program that asks for it is devvm.

devvm doesn’t pin .git/commondir against the VM making one, which would point git on this machine at another config: a file has to be there to be pinned, and devvm puts no file in .git that git doesn’t, so it reports a commondir at each check, as on macOS.

The watch

Where the host can’t pin, devvm locks nothing, and every VM that mounts its folder gets off as its mode. devvm watches the paths it would lock instead, and names what changed after the fact (git_changed), which Linux hosts tells the user how to check.

devvm hashes the same paths that what’s locked lists, found in the same way, and .git/commondir, there or not, the files that include.path and includeIf.*.path lead to in the project folder, and the folder that core.hooksPath names in it. For a hooks folder, it hashes each entry below it, except git’s .sample files, which git never runs, starting with the entries at its top that have a hook’s name (githooks(5)), which git runs, and then the rest. It hashes a regular file’s contents with SHA-256, opened with O_NOFOLLOW and O_NONBLOCK and checked to be a regular file once it’s open (internal/safefile). It records a symlink by where it points, and a path under a symlink, such as .git/config when .git is a symlink, by that fact. When the link resolves to a file or folder inside the project folder, it adds that file’s hash, or a hash of that folder’s hashes, and it never follows a link out of the project folder. Anything else, such as a FIFO, is recorded by its type. The work is bounded: past 1,000 entries, a hooks folder is recorded by that count, its inode and its change time, a file larger than 16 MiB by its size, inode and change time, and a watch keeps at most 2,000 hashes of the folder’s own repo and 200 of each nested repo, so a folder with many nested repos never overflows it. The VM can’t set a change time back over 9p, so a change that keeps a large file’s size is still named. Each check names, in its own warning (git_watch_blind), every path that is a symlink or under one, past a bound, or past the 2,000, because the watch can’t see every change there.

The same checks first run what a lock’s check reports, without locking (protect with watching): a .git replaced since the last check (git_replaced), after which the next check compares with the new one, a commondir (git_commondir), linked worktrees whose commondir leads elsewhere, a repo or submodule git folder that appeared, a submodule’s folder that isn’t a git folder (git_gitdir_not_git), which the watch doesn’t hash as one and where devvm creates nothing, and includes, hook links and core.hooksPath into the project folder. They don’t report hooks in folders that aren’t locked, because nothing is, and the watch names their changes. .git’s identity and the git folders and delegations found are recorded in the git section’s made, as a lock’s check records them. A VM whose made isn’t set yet reports as a new VM does.

The watch reads .git only when the VM is stopped, so it misses a change the VM made and undid before it stopped. It’s a report, not a security boundary.

The hashes go in the VM’s state, in the git section’s watched, by each path relative to the project folder, with scanned set once a check has recorded them. devvm records them when it creates the VM, and checks them again on each launch that finds the VM stopped and on devvm stop, the same places that check the locks on macOS. Each check names every path whose hash changed, appeared or went since the last one, in one warning, at most ten of them and then how many more (git_changed_more), and then records the new hashes. A launch of a running VM checks nothing. A VM whose state has no watched yet, such as one an older devvm made, or one that devvm adopt gave this folder, records its first hashes without naming anything.

Each launch also warns that the VM can change .git (git_unprotected), unless the folder has no .git or the VM is a --clone VM. The warning stops once the user has chosen the mode, which devvm records as the git section’s chosen: devvm git-protect off sets it, and so does --no-git-protect when devvm creates the VM.

What a lock can’t stop

The VM can rename .git and put a new one in its place, add .git/commondir to point git at another config, or do the same with a linked worktree’s folder in .git/worktrees. When devvm creates the VM, and on each launch, it reports a commondir that’s there, linked worktrees whose commondir leads somewhere else, and paths it couldn’t lock because they’re symlinks. devvm reads git’s own small files, a .git file, a commondir and a linked worktree’s gitdir, through a symbolic link as git does, but only when each is a regular file of at most 16 MiB, opened without blocking (internal/safefile), so a FIFO the VM leaves there can’t hang devvm. devvm doesn’t repair anything, so check what it names before you run git in the folder. When you don’t trust what runs in the VM, use --clone, which mounts no .git at all.

The VM writes .git/index, because it has to in order to commit, so it can also add a submodule with its own config, which git status on the host reads. A submodule’s core.fsmonitor therefore also runs on the host. devvm names a new submodule on the next launch, but git on the host reads it before that, unless the VM is strict.

devvm’s own git commands on the host run no program that a repo’s config or .git names, a submodule’s included, whatever the VM wrote there. devvm runs each one with these settings, given as GIT_CONFIG_COUNT pairs, which git takes over any config file:

  • core.fsmonitor=false, core.hooksPath=/dev/null and core.alternateRefsCommand=true, so git runs no fsmonitor, no hook from a hooks folder and no command for an alternate object store’s refs.
  • hook.EVENT.enabled=false for every event githooks(5) lists, and hook.NAME.enabled=false for each hook the repo’s config names, so git 2.54 and newer run no hook that a config defines.
  • filter.NAME.clean, smudge and process emptied, and filter.NAME.required=false, for each filter driver the repo’s config names, so git hashes files without running a filter and doesn’t fail on a required one.
  • protocol.allow=never and protocol.ssh.allow=always, so git reaches nothing but ssh, not a path, file://, ext::, git:// or http. A repo’s config could still allow one protocol by its own key, such as protocol.ext.allow=always, which git takes over protocol.allow, so devvm also sets GIT_ALLOW_PROTOCOL=ssh, which git takes over every protocol setting.
  • maintenance.auto=false and gc.auto=0, so a fetch starts no maintenance or gc.

Its ssh is false, which reaches nothing, in place of a repo’s core.sshCommand (GIT_SSH_COMMAND=false, with GIT_SSH_VARIANT=ssh over a repo’s ssh.variant), unless the command is a --clone VM’s push or fetch, and it fetches nothing lazily (GIT_NO_LAZY_FETCH=1), so a repo that says it’s a partial clone can’t make git rev-list or git status connect anywhere for an object it lacks.

It runs without any GIT_* variable of devvm’s own environment, such as GIT_DIR, GIT_WORK_TREE or GIT_CONFIG_GLOBAL, so a hook or a rebase you run devvm from can’t point it at another repo or config, and it reads your global config from its usual place. It keeps only the absolute folders of PATH, because git looks programs up, ssh among them, from the repo’s folder, and it runs with GIT_TERMINAL_PROMPT=0. Its git status adds --no-optional-locks, so it writes no index, and --ignore-submodules=all, so it never enters a submodule, whose own config could name filters of its own.

A --clone VM’s push adds --no-verify, --no-recurse-submodules and --no-signed, so no signing program runs, and its fetch adds --no-recurse-submodules and an empty --refmap=, so it updates only the branches its own refspecs name, never those of a remote that the repo’s config names after the clone’s address. Both run git with devvm’s own GIT_SSH_COMMAND, which ignores the host, port and options git passes to ssh. It always connects to the VM’s own address and port, the host’s loopback port that the VM’s backend gives, as the VM’s user with the VM’s own key, and it reads no ssh config (-F none). It checks the host keys devvm pinned for the VM’s current start, with the VM’s own known hosts file and no global one, -o HostKeyAlias= the VM’s name and -o StrictHostKeyChecking=yes, and it runs with -o BatchMode=yes, -o ForwardAgent=no and -o ClearAllForwardings=yes. In the VM it runs only git-receive-pack or git-upload-pack, whichever git asks for, on the clone’s path, and it refuses any other command. So no url.*.insteadOf, pushInsteadOf or remote URL in the repo’s config can send the push or the fetch to another host or to another path, and they forward neither your agent nor any port. A repo’s core.sshCommand doesn’t apply, because devvm sets GIT_SSH_COMMAND, and its diff.external, textconv drivers and pager never run, because none of devvm’s commands shows a diff or writes to a terminal.

Before a --clone VM is made, and again before its push, devvm checks that what git reads in the folder is the repo’s own, so the push can’t copy another repo into the VM. The folder’s .git is a folder with no commondir, or it’s the .git file of a linked worktree whose link git made both ways. That .git file names <repo>/.git/worktrees/<name>, that entry’s gitdir file names the folder’s .git back, and its commondir leads to that <repo>/.git, which has no commondir of its own. Neither the git dir nor the common dir has objects/info/alternates, or a packed-refs or reftable that’s a symlink, or anything in objects or refs that’s a symlink, such as a pack folder or a loose object’s folder that leads to another repo’s objects. Then git rev-parse --absolute-git-dir --git-common-dir must name the same two folders. A worktree’s push sends only its branch and that branch’s upstream, when the upstream is one ref, so the repo’s other branches stay on this machine. A branch.<name>.merge that’s a pattern, such as refs/heads/*, would make the upstream push every branch, so devvm then pushes only the branch.

devvm finds the hook and filter names to turn off with one git config before each command, so a VM that keeps swapping the repo’s config could show that git config one config and the command another. Every hook event is turned off by its name as well, which covers config hooks on git that has the event setting, so the gap is a filter that the swap hides, which git status could then run on a file whose stat changed. It needs a VM that writes the repo’s .git, so on macOS, where .git/config is locked, it needs a repo devvm doesn’t lock, such as a nested repo past the walk’s bounds (nested repos).

Two things a repo’s config can still do, and neither runs code. An include.path can make devvm’s git config --get user.name read your name and email from another file in git’s config format, which then go into the VM as its git identity. A config file or included file that is a FIFO makes git, and so devvm, wait until you press Ctrl+C.
