Coding agents

Coding agents

This page explains how devvm gives the coding agents in a VM their settings, logins and history, and what it checks on the way, for the tasks that Coding agents shows. How the proxy holds the agents’ secrets is in agents’ logins and settings.

The guide in every VM

Each launch installs the guide again whenever it differs from devvm’s, and it belongs to root and is read-only, so nothing that the VM’s user runs without sudo can change what the agents read, and a change made with sudo lasts only until the next launch.

Pasting

How devvm paste reads the clipboard, names a copied file, refuses links and finds Linux’s clipboard programs is in the design note on pasting images.

Each agent’s variables

Every VM sets OPENCODE_DISABLE_AUTOUPDATE=1, as it sets DISABLE_AUTOUPDATER=1 for Claude Code, because the agents are read-only shared tools that can’t update themselves, and devvm keeps their versions. For the same reason every VM sets PI_SKIP_VERSION_CHECK=1, so pi doesn’t ask you to run pi update, and PI_TELEMETRY=0, which turns off pi’s report of its install and the attribution headers it adds to some providers’ requests. Claude Code’s telemetry and error reports are off with DISABLE_TELEMETRY=1 and DISABLE_ERROR_REPORTING=1. devvm writes every agent’s variables into each VM at every launch, whichever agents the VM has, and every shell in the VM gets them, login or not, so an agent that an editor’s terminal or ssh runs gets them too. pi would download fd and rg into ~/.pi/agent/bin whenever they’re missing, so base has both, from Ubuntu’s or the container image’s own packages, and pi finds Ubuntu’s and Debian’s fd by its name there, fdfind.

Importing

The import copies only the paths in the store’s table, from ~/.claude, ~/.claude.json, ~/.codex, ~/.config/opencode, ~/.local/share/opencode and ~/.pi/agent, so it never copies your history, such as ~/.claude/projects, ~/.codex’s sessions or ~/.pi/agent/sessions, and never ~/.claude/.credentials.json. Claude Code’s plugin records name the plugins’ folders by their paths, so the store’s copies of the JSON files in ~/.claude/plugins name the plugins’ folders in the store, where the VMs mount them.

A replacement writes each file again and takes out what your home folder no longer has, but it keeps the store’s folders, so a running VM’s mounts still show them. Where the store has a folder and the home folder now has a file, or the other way round, as when a link that led to a folder now leads to a file, the import replaces it.

opencode 2 keeps its logins in its own database rather than in ~/.local/share/opencode/auth.json, so when this machine’s opencode is version 2 or later, devvm reads its logins with opencode auth export and saves them in the store in the format of auth.json, the file that devvm copies for opencode 1. When opencode auth export fails, the import fails too, and the store keeps the login it had.

Links out of an agent’s folder

The import reads each agent’s folder through that folder as an os.Root, so no link inside it leads out of it. A link that leads out is resolved, every link on the way, and only then followed, as links out of an agent’s folder says, and the design note explains why:

  • How it resolves. devvm resolves a link one name at a time, as the system does, and keeps where each link on the way is, so it sees a link that a VM put in its project folder even in the middle of a chain. It compares a target with the refused places and the VMs’ folders by name and by identity, so another spelling of a folder, such as ~/.SSH on a Mac, where case doesn’t count, is still that folder.
  • Where it reads. devvm opens the folder it reads the link’s target through, a follow-links folder, the linked folder or the linked file’s own folder, one folder at a time from /, each opened from its parent and never through a link, so a link that a VM swaps into that path fails the import rather than lead elsewhere. It lists what the link leads to through that folder as a root, and reads each file without blocking, refusing a FIFO, a device or a file that changed into a link as it opened it.
  • What it lists. A linked folder’s folders and files are listed under the link’s own path, and a link inside it is listed as a file when the root resolves it to a regular file. Anything else is left out with a warning.
  • The bounds. It counts every file and folder it lists, and the size of every file, across all the links of one import, and leaves out a link that would pass 20,000 entries, 128 MiB or a file of 16 MiB, the bounds of saving a VM’s settings. A file that grows past them between the listing and the read fails the import.
  • A VM’s folder. It reads the state of every VM devvm has, and warns once for each link and VM when the link’s target is in that VM’s project folder or holds it, or when a link inside a linked folder resolves into it.

Saving a VM’s settings

The save reads only the settings in the store’s table from the VM’s home, and never the logins, so it never reads your history, ~/.claude/.credentials.json, ~/.codex/auth.json, opencode’s auth.json or pi’s. From the VM’s ~/.claude.json it keeps only the settings, account state and MCP servers, as the import does, and the VM leaves out its per-project entries before it sends anything. devvm puts that part in the store’s logins folder, where the import keeps it too. A folder that the store already has is mounted read-only in the VM, so the agent there can’t change it, and the save leaves it as it is. A folder that the store doesn’t have yet is the VM’s own until you save it, and once the VM next starts with the store’s new folder mounted, its setup links that folder in place of its own (mounts).

devvm treats everything the VM sends as untrusted, because the agent in the VM could have changed any of it. It reads at most 128 MiB from the VM, in at most 20,000 files, folders and links, none of the files larger than 16 MiB, and when the VM sends more, or sends a path outside the agents’ settings or a name with a character that a terminal wouldn’t show, devvm saves nothing. Each file it saves is yours alone (mode 600), or mode 700 when it was executable in the VM, so it never keeps a set-user-ID or set-group-ID bit. A link in a settings folder that leads to a file in the same folder becomes a copy of that file. devvm leaves out any other link, any other kind of file, such as a socket, and a settings file that it can’t parse whole, such as a settings.json that isn’t JSON, and it warns you about each. When it leaves out a file in a folder, the store keeps its own copy of that file. A settings file that the VM doesn’t have stays in the store. A folder that the VM sends replaces the store’s folder whole, so devvm writes each of its files again and takes out the files that the VM’s folder doesn’t have, but it keeps the store’s folder itself, so a running VM’s mounts still show it.

The VM’s copies of the settings files and of ~/.claude.json hold placeholders, such as devvm-redacted, where the store has your secrets. devvm puts the store’s secret back in place of each placeholder, as long as the VM’s copy had that placeholder in that place and nothing around it changed, such as the URL of the MCP server that a header is for. When something around a placeholder changed, devvm leaves the whole file out and warns you, so a VM can’t send a secret it never saw to another host, and you can make that change in the store’s file yourself. devvm also leaves out any other file that holds a placeholder, such as a skill. No VM gets opencode’s files in ~/.config/opencode that are neither settings nor Markdown, such as a .env, so devvm leaves out the VM’s own file of that name and keeps the store’s.

Mounts

Absolute paths in the mounted folders, such as Claude Code’s plugin paths, still work, because each is mounted at the same path as in the store on this machine. The VM follows a symlink in these folders among its own files, so a link to a file outside the folder, by a relative or an absolute path, doesn’t reach that file on this machine, on macOS’s virtiofs mounts and on Linux’s 9p mounts alike. devvm doesn’t mount a folder whose path has a comma, on any backend, and it warns you. Lima can’t mount such a path (Lima’s limits).

Copies

devvm merges the settings and MCP servers from the store’s .claude.json into the VM’s own ~/.claude.json, so servers added in the VM stay (MCP servers). Your API key, your answers about API keys and your per-project entries never reach the VM. devvm also replaces the secrets in the agents’ settings files with devvm-redacted, and names what it replaced. Those are the values under keys that look like secrets, every env value and header, and the secrets in URLs and in arguments. In other text, such as a hook’s command, devvm replaces the secrets in its URLs, the keys that start like a known key, such as sk- or ghp_, and the credential after Bearer or Basic, and keeps the words around them (keys in settings files). pi’s settings files that can hold a key are settings.json, models.json and mcp.json, so a provider’s apiKey in models.json reaches the VM as devvm-redacted, and pi’s keybindings.json and Markdown files reach it as they are. From the env of Claude Code’s settings.json, the VM gets only Claude Code’s own settings, such as ANTHROPIC_MODEL, the CLAUDE_CODE_*, DISABLE_* and MAX_* variables and those ending in _TIMEOUT_MS, but none whose name marks it as a credential, such as ANTHROPIC_AUTH_TOKEN. It also gets the values that only name where a secret is, base URLs without their passwords, true, false and short numbers. Every other env value, and every env value of an MCP server, becomes devvm-redacted. When devvm can’t parse a settings file to take its secrets out, the VM doesn’t get a copy of it, and neither does it get opencode’s files in ~/.config/opencode that are neither settings nor Markdown, such as a .env. devvm names each file it doesn’t copy, and when it can’t make the copy of a login, it says why.

Claude Code’s login

devvm agent login claude runs Claude Code’s own login in the VM, and the VM’s proxy saves the login as it reaches Claude’s token endpoint, and Claude Code in the VM gets only placeholders. devvm then sets the VM up again, so it uses the login at once, and every other VM with Claude Code gets it from its next launch.

A VM gets either ~/.claude/.credentials.json or CLAUDE_CODE_OAUTH_TOKEN from devvm, never both, because Claude Code would use the token in its environment over the login in its file. A VM that started with the login devvm replaced keeps working, because its proxy puts the login devvm keeps now in place of either placeholder. The VM gets placeholders whatever its network tier.

Codex’s and opencode’s logins

The proxy reads the real API keys and logins from the login files in devvm’s store as it needs them and refreshes ChatGPT logins there. The proxy puts in opencode’s API keys for the providers that API keys the proxy puts in lists, and its OpenAI and GitHub Copilot logins. The VM’s entry for such an API key holds only its type and the placeholder, so the entry’s other fields, such as its metadata, stay on this machine.

The VM’s copy of Codex’s auth.json holds only what Codex needs for its API key and its ChatGPT login: the placeholders, how it logs in, when it last refreshed, and the IDs of the account and the login. devvm keeps every other field on this machine, because the VM’s proxy can’t put it in, and it names those fields at every launch. That includes Codex’s other ways to log in, such as a personal access token or an Amazon Bedrock key, so Codex in a VM can’t use them. devvm treats Claude Code’s account state in ~/.claude.json the same way, so the VM gets only the account fields that Claude Code writes there today, and devvm names any other field at every launch.

devvm keeps every other entry of opencode’s auth.json on this machine too, because devvm doesn’t know which hosts it’s for, so the VM gets that entry without its key or its tokens, and devvm warns you about each at every launch. That’s an API key for any other provider, such as Azure’s or a local model server’s, a well-known login, which an organization’s own opencode config sets up, and any other OAuth login, such as Copilot Enterprise’s. The VM keeps only the fields of a withheld entry that name the account or how it logs in, such as its type, its enterpriseUrl and its expiry, so opencode in the VM doesn’t use that provider.

Logging in

When you approve a browser login, the browser comes back to localhost:1455, where the agent’s own server in the VM waits, so devvm forwards this machine’s localhost:1455, and localhost:1457, which Codex uses when 1455 is taken in the VM, to the same ports in the VM. The forward lasts only while the login runs, and it ends when the login ends, fails or you press Ctrl+C, which ends the agent’s login in the VM too.

Codex in a VM keeps its login in ~/.codex/auth.json, never in a keyring, because devvm sets cli_auth_credentials_store = "file" in the VM’s ~/.codex/config.toml on every launch.

With --api-key, devvm gives the running VM its copy of the login, with a placeholder in place of the key, and the VM’s proxy puts the key in at once. opencode keeps its logins in its own database in the VM, and it reads its auth.json only when it first makes that database, so when opencode has already run in the VM, devvm also gives it the key’s placeholder with opencode auth import. devvm reads at most 1 MiB of what that import prints in the VM, and when it prints more, devvm stops it and fails, so running devvm in the VM’s folder tries again. Every other VM with opencode gets the key’s placeholder at its next launch, the same way, and any credentials that you added to opencode in a VM yourself stay in its database.

Logins made in a VM

When Codex or opencode in a VM logs in to OpenAI, whether devvm agent login runs it or you run it yourself, the VM’s proxy saves the login in devvm’s store, in the agent’s own auth.json, and the agent in the VM gets only placeholders, so on every tier but open the VM never holds the login’s tokens. The VM you logged in from uses the login at once, and every VM with that agent gets it from its next launch. opencode reads its auth.json only when it first makes its database, so in a VM where opencode has already run, devvm adds the store’s logins to opencode’s database at each launch when they changed since the VM last got them, and makes them the ones opencode uses. Credentials that you added to opencode in the VM yourself stay in its database, labeled with your names rather than devvm, and opencode auth switch changes back to one of them. A login that shows a code to type into a browser on any machine works in a VM as it is, such as codex login --device-auth and opencode’s Codex device code login. opencode’s Sign in with ChatGPT doesn’t work in a VM, because it gets its tokens from another endpoint, whose replies the VM’s proxy refuses so that they never reach the VM, so choose one of opencode’s Codex logins instead, as devvm agent login opencode does. A new login replaces the one in the store, together with Codex’s API key, so every VM with the agent uses the account you logged in to last. A VM saves a login only for an agent that it has, so a VM without Codex can’t replace the store’s Codex login, and a VM without opencode can’t replace opencode’s. When a VM sends a login for an agent it doesn’t have, such as one that a program installed in the VM itself, its proxy refuses the login, devvm saves nothing, and the proxy’s own log says so. In a VM with both Codex and opencode, devvm tells their logins apart by the program that sends them. devvm network log shows a login line for each login it saved. On the open tier, a program that goes around the VM’s proxy gets the login’s tokens itself, and devvm saves nothing (logins made in a VM). Claude Code’s logins in a VM are saved in the same way (Claude Code login).

pi’s logins

devvm agent login pi --api-key --provider PROVIDER saves the key in the store’s ~/.local/share/devvm/logins/pi/.pi/agent/auth.json, in pi’s own format, beside pi’s other providers, as opencode’s --api-key does (logging in with devvm agent login). The VM’s ~/.pi/agent/auth.json holds a placeholder in place of each of those keys, and the VM’s proxy puts the key into pi’s requests to that provider’s hosts, on every network tier, and allows those hosts, as the table in API keys the proxy puts in describes. The VM’s entry for such a provider holds only its type and the placeholder, so it gets none of the entry’s other fields, such as its env, whose values pi uses before the environment’s, and the store keeps them on this machine.

devvm keeps every other entry of pi’s auth.json on this machine too, and the VM gets that entry without its key, its env or its tokens, and devvm warns you about each. That’s an API key for any other provider, such as a local model server’s, a key that’s a command for pi to run, such as !security find-generic-password, and a key that pi fills in from a variable, such as $KEY or ${KEY}, even for a provider whose key the proxy puts in, because devvm can’t tell what pi would send. The VM keeps only the fields of a withheld entry that name the account or how it logs in, such as its type, its accountId and its expiry.

pi’s Claude and ChatGPT logins use the same token endpoints as Claude Code’s, Codex’s and opencode’s logins, whose replies the VM’s proxy captures for those agents, and devvm never keeps such a login as pi’s. In a VM that also has the matching agent, Claude Code for a Claude login and Codex or opencode for a ChatGPT login, the proxy saves pi’s login as that agent’s own, in place of the one devvm keeps for every VM with that agent. In a VM with none of them, the proxy refuses pi’s login and devvm saves nothing (logins made in a VM).

Cursor’s CLI

The VM’s proxy puts the real login only into the requests for the methods that devvm found the CLI calling in its package, on Cursor’s API, its agent’s hosts and its codebase indexing, and into no other. It refuses every other request below /auth/ on those hosts, the methods that make or show a key, a token, a secret or a sign-in, the methods that change your account, and any path it can’t read as Cursor’s hosts do. Those are the real control. As a defence in depth, the proxy also reads every reply from those hosts as it passes, its headers and the agent’s streams included, and cuts one off where a token starts. devvm checked this against one release of the CLI, by reading its code, and against Cursor’s own answers to a login that isn’t there, so a method that Cursor adds that hands out a token in a shape devvm doesn’t know would reach the VM. Such a token would work without the proxy, so if you suspect that one reached a VM, log in again with devvm agent login cursor (logins made in a VM). Neither does devvm guard Cursor’s hosts that the CLI doesn’t use: if one of them also answered /auth/poll, a VM could finish a login there and keep its tokens, though none is known to.

Your Cursor agents on every machine and in the cloud share Cursor’s agent store, your cloud agents follow the skills in it, and your team shares a store of its own, so a VM that could write there could leave instructions for them. So no VM gets the store (why).

API keys

The proxy puts in opencode’s and pi’s API keys for the providers that API keys the proxy puts in lists, in the headers it names. OpenRouter’s key goes in either of its two headers, because pi sends it in x-api-key for OpenRouter’s Anthropic models, as Anthropic’s own API takes a key, and in Authorization for every other model. The proxy swaps the placeholder only when the header holds the placeholder and nothing else, or for Authorization, Bearer, one space and the placeholder, which is how opencode and pi send each of these keys. A header that holds anything else beside the placeholder, or a second header of the same name, keeps the placeholder, so code in the VM can’t surround your key with text of its own, which a provider that quotes part of a key it refuses could show back to it.

The placeholder for an OpenAI key starts with sk-, as an OpenAI API key does, because pi takes an OpenAI key that starts any other way for a Sign in with ChatGPT login and then leaves settings such as the longest reply it wants out of its requests.

The placeholder keeps a key out of the VM only from the launch that first gives the VM the placeholder. A VM that was given one of these keys as it was before then, such as through [pass-keys] when the proxy didn’t put that provider’s key in, may still hold copies of it. They can be in opencode’s database, its write-ahead log and its freed pages, in the disk’s free space and anywhere that the VM’s own code copied the key. While opencode in the VM fails to import the placeholder, devvm’s record of opencode’s last import, ~/.local/state/devvm/opencode-import.json, holds the key too.

With some of these keys, code in the VM can make a credential of its own that works without the proxy. Google Gemini’s key gets an ephemeral token for Gemini’s Live API, which lasts up to about 20 hours and allows as many uses as the VM asks for. xAI’s key gets a realtime client secret that lasts as long as the VM chooses, and OpenAI’s key gets one that lasts up to 2 hours. opencode’s experimental voice mode asks for these itself, so the proxy allows those requests (attack vectors). Some of these providers’ own tools also fetch the URLs that a request names, such as Google Gemini’s URL context and Search grounding, xAI’s live search, Groq’s compound models and Mistral’s agents with web search, so code in the VM can reach hosts that the allowlist doesn’t have through them, as it can through Anthropic’s and OpenAI’s.

History exports

The agents’ logins aren’t in the export, which leaves out ~/.claude/.credentials.json, ~/.codex/auth.json, and opencode’s auth.json, account.json, mcp-auth.json and bin, and holds nothing of ~/.pi/agent but its sessions, so pi’s auth.json stays out too. opencode keeps its sessions and its logins together in one database, ~/.local/share/opencode/opencode.db, so the export holds a copy of that database without its logins. The VM makes the copy with sqlite3, which every base image has, and the copy has no logins, API keys or opencode account in any part of the file, not even a key you typed into opencode in the VM, while the VM’s own database keeps them (how). The export never holds the database’s -wal, -shm or -journal files, which can hold logins that opencode saved last. When the VM has no sqlite3, such as a VM made from an image built without it, the export leaves the database out, so opencode’s sessions aren’t in it, and the run log says so. devvm starts a stopped VM for the export as a launch does, so it locks the folder’s .git again and checks the VM’s confinement first, and the VM stays running. devvm writes the file only once the export is complete, so a failed export leaves no file and leaves an existing FILE as it was. An export holds at most 2 GiB, because a VM could otherwise write until this machine’s disk is full. When the VM sends more, devvm stops the export and keeps nothing of it, so devvm history export fails, while devvm rm and the commands that make a VM again warn that they kept no export and go on without one. Only you can read the file, and devvm makes the exports folder yours alone each time it writes one there, whatever its mode was before. When FILE is in a folder of your own, that folder keeps its mode. If the export fails, devvm rm keeps the VM, and devvm rm --no-export deletes it without exporting. devvm rm VM, for a VM whose folder is gone, exports in the same way, but only from a running VM or a --clone VM, because starting any other would make its folder again (a VM whose folder is gone).

Importing history

The import works on every VM, whether its base is Ubuntu’s image or a Debian-, Ubuntu- or Alpine-based container image (starting from a container image), because it unpacks the export with GNU tar, which Debian and Ubuntu always have and which devvm installs in every base made --from alpine.

An export holds what a VM wrote, so devvm treats it as untrusted. Its transcripts can hold what the old VM’s agents read, and a VM on a less strict tier reaches more, such as your local network on the open tier. So when the export comes from a VM on a less strict tier than the VM you import it into, going from open to internet, allowlist and none, devvm warns you before it imports. devvm knows an export’s tier only from the .folder file beside it in ~/.local/share/devvm/exports, so it warns about an export with no tier recorded, or any FILE elsewhere, such as in the project folder that a VM can write, as if it came from an open VM. devvm never unpacks an export on this machine. It streams the file into the VM as it is, and the VM’s own tar unpacks it there as the VM’s user, so it can only write what that user can write. Before unpacking anything, the VM lists the paths in the export, and when one of them is outside ~/.claude, ~/.claude.json, ~/.codex, ~/.local/share/opencode, ~/.local/state/opencode, ~/.pi/agent/sessions and ~/.cursor/chats, starts with / or has a .. part, devvm imports nothing and says so. It leaves out of that check, and never unpacks, the AppleDouble files whose names start with ._, which macOS’s tar puts beside each file that has extended attributes, so an export you packed yourself on a Mac imports. The import keeps no owner or mode from the export, so the VM user’s umask applies and no file is set-user-ID. It also takes out every symbolic link that points outside the folder it’s in, which is any link to an absolute path or one with a .. part, so an agent writing to a session file can’t follow a link out of its history. An export that devvm didn’t write, such as a .tar.gz you made yourself, can hold opencode’s database with its logins, so the import takes out the database’s -wal, -shm and -journal files and puts in a copy of the database without its logins, as the export makes it, or leaves the database out when the VM has no sqlite3. opencode in the new VM then reads the logins that devvm gave the VM, as it does when it first makes its database. When the VM already has an opencode database, it keeps its own, and opencode’s sessions from the export aren’t imported.
