Maintaining

For maintainers: version bumps and releases. Run the scripts with mise, which puts the pinned GoReleaser and minisign on PATH: mise exec -- scripts/release.sh.

Updating pinned versions

scripts/bump.sh moves every version pinned in the repo, so preparing a release’s pins is one command:

scripts/bump.sh --check         # every pin, by group, against upstream; changes nothing
scripts/bump.sh                 # every patch and minor bump, then a summary for the commit message
scripts/bump.sh docker mermaid  # only these tools, with a named images or e2e tool's major
  • --check prints each group’s pins under its name in brackets, such as [go], with each pin’s current version and upstream’s newest, and whether a bump would be a patch, a minor or a major, or a new digest, commit, checksum or release for a pin that isn’t a version. A held pin says which version holds it, and a line that the run wouldn’t apply says how to apply it. When upstream’s latest is older than a pin, as when a release marker hasn’t moved yet, --check says the pin is newer and bump.sh leaves it as it is.
  • With no tools named, bump.sh applies every patch and minor bump, and never a major, a held pin or a tool that it applies only when named. Naming an images or e2e tool applies its major too. e2e-tools always applies one, because users get the shared tools’ new majors as well, and assets/shared-tools/mise.toml holds what stays.
  • It writes a value only if it has the shape of a pin (a version, a 64-hex checksum, a dated release, a commit, an image digest), since some of the edited files run on the host, and it edits nothing unless every value is good. Then it runs the commands that finish a bump: mise lock for Go and the dev tools, go get and go mod tidy for the modules, go get and hugo mod tidy in docs/ for Hextra, and actionlint and zizmor for the workflows. If one of those fails, the pins are already edited, and it says so.
  • It needs curl and jq, mise for Go, the dev tools and the end-to-end lock, go to apply the modules and Hextra, and gh for the actions.
  • Every Monday the Pins workflow (.github/workflows/pins.yml) runs scripts/bump.sh --check and opens or updates one issue, “Pinned versions to bump”, which lists the outdated pins under their groups, and closes it once none is left. It never bumps anything: you run scripts/bump.sh, then the --from tier of the end-to-end tests when an images or e2e pin moved, because those bumps change images.

The tools, by group, as --check prints them:

  • go moves Go to its newest patch release of the minor that go.mod names: the go lines of go.mod and docs/go.mod, mise.toml’s go, and its mise.lock entries, from go.dev/dl. --check reports a newer minor on the go-minor line, and scripts/bump.sh go-minor moves the same files to it.
  • go-mods moves go.mod’s direct modules, the ones the depguard allowlist allows and the tests’ own, to their newest patch or minor release from the Go module proxy, with go get and go mod tidy. The indirect ones move as go mod tidy needs them. A module’s next major has a new path, so --check reports it and you move it by hand. deadcode moves the deadcode task’s version in mise.toml to golang.org/x/tools’ newest release.
  • dev-tools moves each of mise.toml’s tools but Go to mise’s newest version of it, edits its line and runs mise lock, so mise.lock keeps every platform’s checksum, and markdownlint-cli2’s lock folder in .mise/locks/ moves with it.
  • ci-mise moves the version that the workflows give jdx/mise-action to base’s mise, as the run leaves it, so scripts/bump.sh mise ci-mise moves both. actions moves each workflow’s uses: to its newest release’s tag, as the tag’s commit from gh api, with the tag in the comment after it, and reports a newer major without applying it.
  • hextra moves the docs site’s theme in docs/go.mod, and it reminds you to compare the copies of Hextra’s files in docs/layouts/ with the new release’s. mermaid moves the Mermaid version in docs/hugo.yaml, only when named, because its diagrams need a look on the built site.
  • cursor moves Cursor’s CLI, only when named, to the release that Cursor’s install script fetches, with each platform’s SHA-256 computed from its download, because Cursor publishes no checksums. devvm’s login and proxy code was read against the pinned release, so read the new one where that code names it, then run e2e-tools.
  • A hold keeps a pin below a version, and --check shows the newest version beside it. Go modules and actions take Dependabot’s ignore list in .github/dependabot.yml, which keeps pflag below 1.1.0, because pflag 1.1 prints every boolean flag with [=true|false] in the help. The other holds are in bump.sh’s holds, which keeps Node, the one in mise.toml, on its major.
  • bump.sh’s header lists every pin with the tool that moves it, or with - and the reason it’s left, as # pin lines. TestBumpCoversPins in internal/structure finds the pins in assets/, mise.toml, both go.mod files, the workflows, tests/e2e-mise.lock, tests/e2e’s consts and docs/hugo.yaml, without the network, and fails on a pin that no line covers or on a line that covers nothing, so a new pin gets a tool or a reason. The header also says why the pins outside those files are left as they are, such as the Lima that install.sh installs, which is the newest release checked against its SHA256SUMS, and the Homebrew formula, whose URLs and checksums release.sh fills in.
  • base’s Ubuntu cloud image and its apt packages have nothing to bump: devvm pins the newest image on each machine at its first build of base, and records the newest packages for each key of base at its first build (Ubuntu’s cloud image, base’s packages). docker moves Docker’s packages (assets/layers/docker.sh), read from its repository for base’s Ubuntu release, and its signing key. Packages added to assets/layers/base.sh or assets/features/ need no pin of their own: they change base’s key, whose first build records them.
  • mise moves base’s mise (assets/layers/base.sh) and devvm’s host mise (internal/tools/mise.go) together: the host one writes the lock base’s installs from. TestMisePins fails when their versions or Linux checksums differ, and base’s mise version is in the key of each tool image mise installs, so a bump builds them again.
  • The shared tools aren’t pinned for users, but for Cursor’s CLI: holds go in assets/shared-tools/mise.toml (node = "24" stays on that major). testdata/mise.lock is a fixed lock for the tests.
  • Their backends are named in mise.toml’s [tool_alias] table, for every tool that isn’t one of mise’s own core: tools, because mise’s registry can move a tool to another backend in any release (versions). A new shared tool gets its alias there, and TestToolBackendsNamed fails when a tool that isn’t a core: tool has none, or when its alias isn’t the backend that tests/e2e-mise.lock resolved.
  • When opencode’s major version changes, or a bump of e2e-tools moves opencode to a version that adds migrations, refresh internal/vm/testdata/opencode-<version>.sql, the schema of opencode’s database that TestOpencodeCleanSchema cleans. Print it with sqlite3 ~/.local/share/opencode/opencode.db .schema in a VM with that opencode, after opencode auth list has made the database, and copy only the schema, never rows. Name the file for the version, and in the test put each new table in its list of tables that devvm empties or keeps, which the test asks for. A table or a column that holds a login also goes into opencodeLogins (internal/vm/agents.go) and the design note’s opencode’s database in history exports.
  • e2e-tools, e2e-from, e2e-curl and e2e-ubuntu move the end-to-end tests’ own pins, which keep their cached images valid between runs: e2e-tools resolves tests/e2e-mise.lock again, with devvm’s pinned host mise, for both architectures’ glibc and musl VMs, and refuses a tool whose download has no checksum on every platform yet; e2e-from moves the digests of node:24, alpine:3 and ubuntu:26.04 in tests/e2e/from_test.go to Docker Hub’s; e2e-curl moves curlImage in tests/e2e/transparent_test.go, the curl image that the network checks run in containers, to curlimages/curl’s newest release, by its digest; e2e-ubuntu moves e2eUbuntuRelease in tests/e2e/sandbox_test.go, the dated release of Ubuntu’s cloud image that e2e pins base to in place of the newest, to the newest Ubuntu lists. Ubuntu removes dated releases after a few months, and e2e’s going stops its first builds of base: bump e2e-ubuntu before that. Run e2e-tools after any change to assets/shared-tools/mise.toml, because the end-to-end tests refuse a lock resolved from another one (end-to-end tests). mise run test catches it first: TestE2ELockPins checks the lock’s first line against mise.toml and that it locks each of its tools, and TestE2EUbuntuPins checks that e2eUbuntuRelease is a dated release of base’s Ubuntu release, which e2e-ubuntu lists, and that scripts/bump.sh and tests/e2e name only that release.
  • e2e-lima moves the Lima release that CI’s end-to-end workflow installs, LIMA_VERSION in .github/workflows/e2e.yml, to Lima’s newest release, and LIMA_SHA256 to its Linux-x86_64 tarball’s line in that release’s SHA256SUMS. Lima’s release notes print the SHA-256 of SHA256SUMS itself, so e2e-lima checks the downloaded file against that value first and edits nothing when they differ.
  • assets/layers/ubuntu-cloud.gpg is Ubuntu’s cloud image signing key (fingerprint D2EB44626FDDC30B513D5BB71A5D6C4C7DB87C81), from keyserver.ubuntu.com. If Ubuntu changes it, pinning a new image (a first build of base, or devvm rebuild base) stops with ubuntu_bad_signature: fetch the new key, check its fingerprint against Ubuntu’s announcement, and replace the file (gpg --export FPR).
  • assets/layers/ubuntu-archive.gpg is Ubuntu’s archive signing key, “Ubuntu Archive Automatic Signing Key (2018)” (fingerprint F6ECB3762474EDA9D21B7022871920D1991BC93C), fetched from keyserver.ubuntu.com by that fingerprint, checked against the fingerprint that Ubuntu’s security team lists, and exported with gpg --export-options export-minimal --export FPR. devvm checks the InRelease files of a first build of base against it (ubuntu.ArchiveKeyring). If Ubuntu signs the archive with a new key, that build stops with packages_refused: fetch the new key, check its fingerprint the same way, and replace the file. The key must be RSA, because internal/ubuntu/pgp.go checks only RSA signatures. Moving base to a new Ubuntu release (ubuntu.Series, ubuntu.Version) also moves ubuntu.Released, the day Ubuntu released it, which is the date of that release’s own InRelease (dists/<series>/InRelease), because devvm refuses a release pocket dated before it.
  • Edited scripts change image keys, so the affected images rebuild on next use. An edit to assets/prelude.sh changes the key of every image and every shared tool image. Build them in a sandbox of their own (LIMA_HOME, DEVVM_LIMA_HOME, XDG_DATA_HOME, XDG_CONFIG_HOME) before committing (devvm build docker, or a VM made with the tools whose build script changed), then devvm gc, and run the end-to-end tests.

Checking base against Ubuntu’s newest

The end-to-end tests pin base to e2eUbuntuRelease, so they never build base the way a user’s first build does, from Ubuntu’s newest cloud image and the mirrors’ newest packages. An upstream change can break those builds before any test sees it. For example, vz’s direct kernel boot needs an uncompressed arm64 kernel, and a VM shuts down only when its kernel has gpio_keys. mise run e2e -- --newest-base builds base as a user’s first build does and runs the checks that prove it works: images, then project (a VM that boots, stops, starts again and shuts down) and tools. --only chooses other sections in their place.

The run gives devvm no release to pin. It reads the newest release from Ubuntu’s listing, as scripts/bump.sh e2e-ubuntu does, and prints it at its start next to e2eUbuntuRelease. It runs in a sandbox of its own, which is slot 0’s with -newest added to its Lima home, state folder, Keychain service and lock (~/.lt-e2e-go-newest, /tmp/devvm-go-e2e-newest, devvm-go-e2e-newest and /tmp/devvm-go-e2e-newest.lock), with each fixed port slot 0’s plus 1000. So the cached pinned images in the other sandboxes stay as they are. Each run first deletes its sandbox’s images, tool images and package cache, so base is built from nothing, with its packages from the mirrors. The images section checks that devvm pinned the release Ubuntu listed as its newest and that base booted from it. When the newest doesn’t boot, a user’s devvm falls back to the release before it (origin_no_boot), so that check fails on the fallback. Its times go in timings/plain-newest/ in slot 0’s state folder, apart from the cached runs’. --newest-base can’t be combined with --slots or --slot.

Run it before each release and every week or two between them, on an arm64 Mac (vz) and on a Linux host (QEMU) when you can, because the two boot base differently. At its end, it prints the release Ubuntu listed and the release devvm pinned. When a check fails, it says UPSTREAM DRIFT and names the release, because a user’s first build of base gets the same failure now. Then:

  1. Read the failed check’s output and the run log of base’s build, which the build’s output names (log_details), in the sandbox’s state folder under data/devvm/logs/runs/.
  2. Run mise run e2e -- --only images on the pinned release. If it passes, the failure is upstream’s, from the newer image or its packages. If it fails too, the fault is devvm’s own, so fix that first.
  3. Fix devvm for the new release, such as a change to assets/layers/base.sh or to the Lima template. Then run --newest-base again until it passes.
  4. Bump e2e-ubuntu to that release once it passes, so the other end-to-end runs test it too.

Until a fix ships, users can still build base, because devvm’s fallback to the release before covers a newest release that doesn’t boot. A package that breaks base has no fallback, so a fix for one goes in the next release.

Releasing

  • Once, the keys: a minisign key for releases, minisign -G -p packaging/minisign.pub -s ~/.minisign/devvm.key (commit packaging/minisign.pub; the secret key and its password never go in the repo), and a key git signs tags with (git config user.signingkey, GPG, or SSH with gpg.format ssh) that git tag -v verifies on this machine. Commit its fingerprint in packaging/release-signer, one per line (# comments): the GPG fingerprint (gpg --fingerprint, no spaces), or the SSH key’s SHA256:… (ssh-keygen -lf KEY.pub). release.sh refuses a tag signed by any other key, even one git trusts. To rotate, add the new key’s line, tag with it, then remove the old one.

  • Each release: bump VERSION, add the CHANGELOG.md entry and commit it on main. Then tag main’s HEAD with git tag -s v<version> and run mise exec -- scripts/publish.sh, which asks for the minisign password once and asks once more before it publishes anything. The secret key never leaves this machine, and only minisign reads it, so no CI job and no GitHub secret ever has it.

  • If a final release changed the state format, freeze testdata/v<version>/ once the tag exists: run its generate.sh against the tag on a Mac and on Linux, and add its tests, as Freezing a release’s state says. A release that changes nothing on disk adds no fixture, and a release candidate adds none either, because its final release’s fixture holds the state it changed.

  • A prerelease, such as a release candidate or a beta, goes out the same way, with a version of the form x.y.z-<word>.N: VERSION holds 0.2.0-rc.1, CHANGELOG.md gets an entry ## 0.2.0-rc.1, and the tag is v0.2.0-rc.1. The word is lowercase letters, such as rc, beta or alpha, and release.sh refuses any other form of VERSION. scripts/publish.sh marks a prerelease’s GitHub release as a prerelease, passing --prerelease to gh release create and gh release edit, so GitHub’s latest release skips it, and so do the install script’s default, devvm upgrade and the daily release check. In the tap it changes only Formula/devvm-rc.rb, the formula that follows prereleases, in a commit titled devvm-rc <version>, so the formula devvm stays on the last release. At the end, it prints how to check the prerelease with brew upgrade devvm-rc or brew install devvmhq/tap/devvm-rc, and the prerelease’s install script line.

  • The tap’s two formulas are devvm, the newest release’s, and devvm-rc, the newest prerelease’s or release’s, whichever is newer. devvm-rc only moves forward: each publish, a release’s or a prerelease’s, points Formula/devvm-rc.rb at the version it publishes, unless the tap’s devvm-rc already names a newer one. So a release moves devvm-rc users onto it once it’s newer than their prerelease, and a patch release of an older line, or a prerelease older than the tap’s, leaves devvm-rc where it is. The printout says which way it goes, and when nothing in the tap changes, as for such a prerelease, it has no tap step and prints the install script line and devvm upgrade --to for checking it.

  • A prerelease’s changelog entry lists what changed since the version before it, whether that’s a release or another prerelease, and it becomes that prerelease’s notes on GitHub. When the release itself goes out, its entry, such as ## 0.2.0, replaces its prereleases’ entries and lists everything since the last release, so someone who upgrades from that release reads one entry. Each prerelease’s notes stay on its GitHub release.

  • Before it builds, scripts/publish.sh checks what it needs and stops with nothing done when a check fails. The tag v<version> has to pass release.sh’s own checks, so it exists, is signed, and is signed by a key in packaging/release-signer. The tag’s commit has to be main’s HEAD, and origin’s main has to be an ancestor of it, so that the push is a fast-forward. If origin already has the tag, it has to be the same tag. The working tree has to be clean, gh has to be installed and logged in (gh auth status), and minisign has to be installed. A published GitHub release for the tag is refused unless it already has every file, which is the case when an earlier run stopped after it, and unless GitHub marks it as a prerelease exactly when the version is one. The refusal names the gh release edit command that fixes the mark. The tap’s checkout, a clone of devvmhq/homebrew-tap, has to exist, be clean and be on main, for a prerelease too, and its origin has to have no commits that its main lacks. The checkout is DEVVM_TAP_DIR, or ../homebrew-tap next to this repo by default.

  • Then it builds and shows the release. It runs scripts/release.sh, which builds dist/ and signs SHA256SUMS, and where minisign asks for the password. It prints the version, the tag’s commit, each file with its size and SHA-256, the release notes, which are the CHANGELOG.md entry for the version, and the tap’s changes as a git diff of each formula it writes: Formula/devvm.rb for a release, and Formula/devvm-rc.rb, with a line saying when a release moves it too, or when it stays on a newer version. It lists the four steps, each marked done or to do, and when nothing in the tap changes, the fourth says so. Then it asks Publish devvm <version>? [y/N] on the terminal, and any answer but y stops it with nothing published. --dry-run stops before the question, so it pushes and publishes nothing and makes no commit in the tap, and --help describes the script.

  • Then it publishes, in this order. It pushes main and then the tag to origin. It makes the GitHub release devvmhq/devvm v<version> with gh release create --verify-tag, titled devvm <version>, with the release notes and the archives, the source tarball, SHA256SUMS, SHA256SUMS.minisig and install.sh. The release starts as a draft and is published only once every file is uploaded, so nobody sees a release that is missing files. Last, it copies dist/devvm.rb to the tap’s Formula/devvm.rb and dist/devvm-rc.rb to its Formula/devvm-rc.rb, each only when it’s one the tap gets and it differs, commits them in one commit, devvm <version> for a release or devvm-rc <version> for a prerelease, with the tap’s own commit signing, and pushes the tap. It uses gh for GitHub and never puts a GitHub token on a command line. At the end it prints how to check the release: brew update && brew upgrade devvm, or brew trust --formula devvmhq/tap/devvm and then brew install devvmhq/tap/devvm, with devvm-rc in place of devvm for a prerelease, and the install script’s curl line.

  • When a step fails, it says which steps it published and which it didn’t. Fix what failed and run it again, because every step skips what’s already done: a pushed main or tag, a published release whose SHA256SUMS matches the new build’s, and a tap whose formulas are already this build’s. A draft release that an earlier run left gets this build’s files again before it’s published. A release published from another build, whose SHA256SUMS doesn’t match, is refused. To finish by hand instead, run the steps it didn’t do in order: git push origin main, git push origin v<version>, the gh release create above (or gh release upload --clobber to a draft, then gh release edit v<version> --draft=false), each with --prerelease for a prerelease, and then copy the formulas the printout listed, dist/devvm.rb and dist/devvm-rc.rb, to the tap’s Formula/, commit them and push it.

  • scripts/release.sh checks the tag with git tag -v and its signer against this checkout’s packaging/release-signer, then builds dist/ from the tagged commit with GoReleaser (.goreleaser.yaml), in a clone of its own, so only what’s committed goes in, with one goreleaser release --skip=publish. It checks that the binary built for this host prints the version, writes install.sh and adds its checksum to SHA256SUMS, then signs SHA256SUMS with ~/.minisign/devvm.key (or DEVVM_MINISIGN_KEY) and verifies it with packaging/minisign.pub. Nothing is published, because publishing is scripts/publish.sh’s. scripts/release.sh --check runs only the tag’s checks and the build’s preconditions, prints the tag’s commit and builds nothing, and scripts/publish.sh runs it first.

  • dist/ then holds:

    FileWhat
    devvm-<version>-<os>-<arch>.tar.gzthe binary, its files (assets/) embedded, with README.md, CHANGELOG.md and LICENSE, for darwin and linux, arm64 and amd64
    devvm-<version>.tar.gzthe source, attached to the release for whoever wants to build devvm themselves
    SHA256SUMS, SHA256SUMS.minisigtheir checksums and install.sh’s, and the signature
    install.shthe install script, set to this release and to packaging/minisign.pub’s key
    devvm-rc.rbthe Homebrew formula devvm-rc, which follows prereleases, set to each platform’s archive, its URL and its checksum from SHA256SUMS
    devvm.rbfor a release, not a prerelease, the Homebrew formula devvm, set the same way

  • scripts/release.sh --head builds from HEAD’s commit instead, for testing, with VERSION’s version, a release’s or a prerelease’s. It’s unsigned unless DEVVM_MINISIGN_KEY names a test key; DEVVM_MINISIGN_PUB names its public key in place of packaging/minisign.pub. DEVVM_RELEASE_URL points the formula at a test location. A commit without install.sh is refused.

  • scripts/release.sh --formula-from DIR writes only the formulas, for VERSION’s release once it’s published, and builds nothing: dist/devvm-rc.rb, and dist/devvm.rb too when VERSION isn’t a prerelease. Download the release’s SHA256SUMS and SHA256SUMS.minisig into DIR first. The script checks the signature against packaging/minisign.pub, and that its trusted comment is devvm <version> for VERSION’s version, so it refuses another release’s files. Then it fills in the formulas the same way a build does, from that SHA256SUMS.

  • To try dist/install.sh on such a build, copy dist/ to DIR/releases/download/v<version>/, then in a throwaway HOME with DEVVM_PREFIX under it: DEVVM_INSTALL_TEST=1 source dist/install.sh, set repo_url=file://DIR and protos='=https,file' (it downloads over HTTPS only), and run main --no-deps. Without --no-deps it offers to install what the host lacks: answer no, or run it with no terminal.

  • Every build sets the version with -X github.com/devvmhq/devvm/internal/cli.version=<version>: devvm doesn’t read VERSION. The formula template (packaging/homebrew/devvm.rb) is both formulas’ one source, and it builds nothing. It has an archive for each of macOS and Linux on arm64 and Intel, the same archives the install script installs, and it installs the binary alone from the one for this machine. release.sh fills in each formula’s class, Devvm or DevvmRc, and the other formula, which it conflicts with by its full name, devvmhq/tap/devvm-rc or devvmhq/tap/devvm, because both install the devvm command. It also fills in each archive’s URL and its checksum, which it reads from the SHA256SUMS it just wrote, on every line that isn’t a comment. Both generated formulas pass brew audit --strict --online and brew style.

  • Publishing is the maintainer’s call, so an agent asks first and never runs scripts/publish.sh without --dry-run on its own. The script’s tests (testdata/script/publish.txtar) run it against a local bare repo as origin, a local bare tap and a fake gh.

The docs sites

The docs have two sites, and the Docs workflow (.github/workflows/docs.yml) deploys both. devvm.dev shows the docs of the latest release, so what users read matches the devvm they install. next.devvm.dev shows the docs on main, for the next release, which is what someone trying a prerelease reads. A pull request that touches the docs gets their lints and a build, and it deploys nothing, so a pull request from a fork never reaches either site or its keys.

  • devvm.dev is GitHub Pages, in the repo’s github-pages environment, which accepts deployments from main and from v* tags, and only admins can create a v* tag. When a release is published, and it isn’t a prerelease, the workflow builds the docs in that release’s tag and deploys them. A release event runs the workflow file that the tag has, so a release whose tag predates this workflow doesn’t deploy on its own. Pushes to main never change devvm.dev.
  • To deploy a release’s docs by hand, for a release that didn’t deploy on its own or to put devvm.dev back on a release, run the Docs workflow from main in the repo’s Actions tab, or with gh workflow run docs.yml --repo devvmhq/devvm -f site=devvm.dev -f ref=v0.1.0. The site is devvm.dev unless you choose another one, and the ref is the release’s tag, which has to look like v0.1.0, so a prerelease’s tag is refused. Without a ref, the workflow deploys the latest release, as gh release view names it.
  • next.devvm.dev is Cloudflare Pages, serving the files on the main branch of the repo devvmhq/docs-next, and Cloudflare builds nothing. On each push to main that touches the docs, the workflow lints and builds main’s docs for next.devvm.dev, then replaces everything in devvmhq/docs-next but its README.md with the build, and commits it as Build from devvm <short sha>. When the build is the same as the last one, it commits nothing. gh workflow run docs.yml --repo devvmhq/devvm -f site=next.devvm.dev runs it by hand. Nobody edits devvmhq/docs-next by hand, because the next build replaces it.
  • The deploy key that pushes to devvmhq/docs-next is the secret DOCS_NEXT_DEPLOY_KEY in the docs-next environment, which only main can deploy from. It’s an ed25519 key with write access to devvmhq/docs-next and to nothing else. The workflow checks that repo out with it only after the site is built, so the build never sees the key. To rotate it, make a new key, add its public half to devvmhq/docs-next as a deploy key with write access, put its private half in the secret, then delete the old deploy key.
  • The next build is hugo -s docs --minify --config hugo.yaml,next.yaml, which reads docs/next.yaml over docs/hugo.yaml. It sets the site’s address to https://next.devvm.dev/ and puts a banner on every page that says these docs are for the next devvm and links to devvm.dev. It also sets noindex, so Hextra gives every page a noindex, nofollow robots meta tag, and docs/layouts/robots.txt disallows everything, so search engines don’t index the site. devvm.dev’s build, hugo -s docs --minify, never reads docs/next.yaml, so it has no banner, its pages say index, follow, and its robots.txt allows everything.
