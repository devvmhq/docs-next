The structure test

internal/structure parses every Go file in the repo, tests and every platform’s included, generated files left out, and checks what linters don’t. mise run test runs it. Each failure starts with its rule and the file and line:

RuleChecks
max-methodsno type has more than 24 methods, value and pointer receivers together, and no interface declares more than 24, not counting the interfaces it embeds; a larger one splits by what its methods do
no-initno func init()
package-varsa package-level var is a blank interface check, an Err*/err* sentinel from errors.New or fmt.Errorf, a regexp.MustCompile, template.Must or sync.Once* result, a //go:embed file, or listed in allowedVars; anything else becomes a field, a const or a local
layerswhich packages import which, in non-test files (tests may wire packages together)
ownersin non-test files, only its owner runs a host command that commands lists, only the files execSites lists make a host command, only guardOwner asserts a backend package’s type, only envOwner reads a DEVVM_ variable, but the settings envSettings lists, only its file in envOwners reads HOME, only its owner’s string literals hold a text that literals lists, only its owner’s string literals are, whole, a name that names lists, only its owner’s calls to package strings split or join on a separator that separators lists, only pathsOwner builds a path in devvm’s data or config folder, and only its file in callers calls a function that callers lists (details)
goroutinesin non-test files, a function that starts a goroutine, with a go statement, a wait group’s Go or time’s or context’s AfterFunc, is in goroutineSites, with what waits for its goroutines to end, or detached: and why nothing does, and a package that starts one calls leaktest.Main in its tests’ TestMain
dropped-errorsin non-test files, no function assigns a Wait’s error, or a strconv parse’s, to _, such as _ = cmd.Wait() or n, _ := strconv.Atoi(s), unless droppedErrors lists it with why, because a failed wait would read as a clean exit and text that isn’t a number as 0
read-limitsin non-test files, every io.ReadAll reads through an io.LimitReader made in its call, such as io.ReadAll(io.LimitReader(r, limit+1)), unless unboundedReads lists its function with why, so a peer or a file that never ends can’t fill the memory
folder-idsin non-test files outside internal/platform, no function compares a folder’s identity or its volume with == or !=, except with "", switches on one, passes one to strings.EqualFold, strings.Compare, slices.Contains or slices.Index, or keys a map by one, whether indexed or in a map’s literal, with its type written out or as a named map type of the module’s. A folder’s identity is a field named Folder or GitID, a call of a state’s Folder or FolderVolume, a call of FolderID, folderID or FolderDevice, or a name in the same function that one of those, or such a name, was assigned to. A function passes when exactFolderIDs lists it with why. The rule is there because a boot can number an unchanged folder’s device anew, which only platform.SameFolder and platform.SameOpenFolder allow for
status-linesin non-test files outside the folders statusFree lists, a function that does slow work shows a status line itself, with a Reporter’s Status, a LoggedCmd step or its Runner’s Run, unless statusSites lists it with why, so the user sees what devvm waits for (status lines). Slow work is making a host command with exec.Command or exec.CommandContext, running host git through internal/hostgit, walking a folder with fs.WalkDir, filepath.Walk, filepath.WalkDir, hostsafety.Walk or safefile.Walk, looking up a volume with platform.VolumeUUID, making a request with internal/fetch’s Open, Resolve, Get or Download, waiting for a lock with platform.LockFile, LockFileShared or LockDir whose waiting is nil or platform.NoWait, or running a backend’s command outside a step with its Runner’s Output or Attach

The layers:

  • Only cmd/devvm and internal/cli import internal/ui; only internal/cli imports internal/vm; only cmd/devvm imports internal/cli.
  • internal/backend/... imports none of internal/vm, build, tools, netpolicy, secrets, project, gitprotect, sshconfig, sshagent, trust or vmssh, so the port forwarder and the link sessions stay devvm’s on every backend.
  • Only internal/backend/registry and internal/cli import a backend (lima); only tests import backendtest, internal/leaktest, internal/memnet, and internal/stubtest and the packages below it, which import only internal/msg and each other. The stubs’ binary, internal/stubtest/stub, and its state, internal/stubtest/stubstate, import nothing else of devvm’s, because the binary stands in for the tools devvm runs and is built apart from it.
  • internal/proxy imports no other devvm package except internal/daemon, internal/landlock, internal/redact, internal/safefile and internal/vmname.
  • assets, locales, internal/platform, internal/msg/gen, internal/testbuild, internal/hostgit, internal/shell, internal/vmname, internal/daemon, internal/fetch, internal/jsonc, internal/redact, internal/agents, internal/safefile, internal/landlock, internal/leaktest and internal/memnet import no devvm package; internal/agentlogin only internal/agents, internal/fetch, internal/jsonc, internal/platform, internal/proxy, internal/redact, internal/safefile and internal/state, because it holds agents’ logins; internal/msg only locales and internal/vmname; internal/paths only internal/msg and internal/vmname; internal/state only internal/msg, internal/paths, internal/platform and internal/vmname; internal/image only assets, internal/agents, internal/msg, internal/paths and internal/shell; internal/devcontainer only internal/image, internal/jsonc, internal/msg and internal/shell.

Everything it holds the code to is in devvm() in internal/structure/structure_test.go:

  • largeTypes lists the types allowed more methods, which are paths.Dirs and ui.UI, each with its count as its maximum and why. A backend isn’t one of them, because its methods are split by backend.Backend’s roles (how a backend plugs in). One that grows fails; one that shrinks fails until its maximum is lowered.
  • allowedVars lists the other package-level vars, by package folder and name, each with why: values set by -ldflags, fixed tables, test fixtures. An entry whose var is gone fails.
  • layers is the layering table: a layer’s packages (from, but not exceptFrom) import none of to (but exceptTo); x/... is x and the packages below it.
  • commands maps a host command to the one package that runs it. execSites lists the files that make a host command with exec.Command or exec.CommandContext, each with why, and a listed file that no longer makes one fails. guardOwner names internal/backend/guard.go, the one file that asserts a backend’s type. envOwner names the one file that reads devvm’s DEVVM_ variables. envSettings lists the variables read elsewhere, each with the files that read it and why. A listed file that no longer reads its variable fails. envOwners maps another variable to the one file that reads it, which for HOME is internal/paths/dirs.go.
  • literals maps a text that only one package’s string literals may hold to that package and what the others use instead. names maps a name that only one package’s string literals may be, whole, to that package and what the others use, and namesFree lists the folders whose literals may be one anyway: internal/stubtest, whose stubs are named after the commands they stand in for.
  • goroutineSites lists every function outside tests that starts a goroutine, as its file and its name (internal/proxy/splice.go: splice, or Type.Method for a method). A function literal’s goroutine counts in the function it’s in, or in the package-level var whose value it is. A goroutine starts with a go statement, a wait group’s Go, or time’s or context’s AfterFunc, whose function runs in a goroutine of its own. Goroutines that the standard library starts otherwise, such as an HTTP server’s for each connection, are for the leak checks to find, not the registry. Each entry says what waits for the goroutines to end, such as scanAll's wg.Wait, or starts with detached: and says why nothing does and what ends them anyway, such as a look at a folder whose disk may hang, which folderWithin leaves to finish on its own. A new goroutine fails until its function is listed, and a listed function that no longer starts one fails, so the list stays current. A package that starts a goroutine also fails until a test file of its calls leaktest.Main. The tests’ own goroutines are the leak checks’.
  • droppedErrors lists the functions outside tests that assign a Wait’s or a strconv parse’s error to _, each named as in goroutineSites and with why, and none does today. The check reads no types, so a call of any method named Wait counts, and the parses are Atoi, the Parse functions, Unquote, UnquoteChar and QuotedPrefix. A listed function that no longer drops one fails, so the list stays current.
  • unboundedReads lists the functions outside tests whose io.ReadAll reads with no limit, in the same way, each with why its reader ends: the status line’s look at the end of the run’s own log, which only that run writes, and the test stubs’ reads of the standard input that devvm under test writes and closes. A reader limited before the call, held in a variable, counts as unlimited, so the limit goes in the call itself. A listed function that no longer reads with no limit fails.
  • exactFolderIDs lists the functions outside tests and internal/platform that compare a field named Folder or GitID with == or !=, in the same way, each with why: the agents’ and exports’ fields of that name, which are paths, recordMove’s check that the state is as it was read, and folderChanged, which runs after a start recorded the folder’s identity as it is now. The check reads no types, so any field by those names counts. A listed function that no longer compares one fails.
  • statusSites lists the functions outside tests that do slow work and show no status line of their own, in the same way, each with why: the status line of the caller it runs under, named by its message, such as checking_vm for a launch’s checks of the project folder, work that takes the terminal, such as ssh-add asking for a passphrase, a process with no UI, such as a forwarder or a link session, or a command made for its caller to run. statusFree lists the folders whose code shows none, each with why: internal/ui, which draws the status line, the proxy’s and devvm’s background processes, internal/hostgit and internal/fetch, whose callers’ functions are the sites, and the tests’ stubs. The check reads no types, so it doesn’t see a backend’s methods, such as Exec, which TestLaunchStatusLines checks for a launch, and a caller’s status line is only named, so a reviewer checks that it covers the call. A listed function that no longer does slow work without one fails.
  • callers maps a function to the one file outside its package that calls it, and a listed file that no longer calls it fails. A method is listed as pkg.Type.Name, such as internal/paths.Dirs.AgentSettings, and any call of a method by that name outside its package counts, because the check reads no types, so a listed method’s name is its type’s alone.

TestRulesFail breaks each rule, and each layer, on small sources and checks the failure names it.

Shell scripts that live in Go strings get shellcheck too, since lint’s shellcheck only finds files with a shebang. TestEmbeddedScripts in internal/structure finds every call site that runs a script as sh -c, /bin/sh -c or bash -c (or -lc), in a []string literal or a call’s arguments, outside tests and the stubs. When the script is a constant, a literal, or a sum of them, such as seedApply with seedMarker in it, the test writes it to a file and runs shellcheck -s sh or -s bash, as its shell reads it, at -S warning, skipping when shellcheck isn’t installed. A script built at run time can’t be read there, so the test fails on one until dynamicScripts lists its file and expression with why: a fixed command around quoted paths, a devcontainer’s own command, or a builder that a test of its package checks, as internal/vm’s TestBuiltScriptsShellcheck does for the scripts built from the agents’ registry. A listed site that’s gone fails too, so the list stays current. A shell given any other flag, such as sh -ec or sh -e -c, fails as well, because the test would miss its script: put options such as set -e in the script instead. -s, for a script on standard input, is fine.

One owner for each concern

Each concern in devvm has one owner, the package or function that does it, such as internal/hostgit for every git command devvm runs on the host, internal/paths for every folder and file devvm uses, internal/settings for every default (settings.Read and settings.Save, over config.toml and settings.json, with each value’s parser), and locales/en.toml for every message. Before you add a helper, a parser, a path, a file reader, a message or a table, find its owner and extend it. A second copy drifts from the first, and then one of them is wrong. Code with no owner yet can have a second copy, because a copy can be cheaper than the wrong shared helper, so extract an owner at the third copy. A judge, such as proxy.Public or NormHost, gets its owner at once, because its two copies would disagree on what’s allowed. The packages says what each package owns, and the failures of the checks below name the owners too.

The packages

Each package owns these concerns, and a package’s doc.go, where it has one, maps the package itself. internal/fetch, internal/redact, internal/agents, internal/jsonc, internal/shell, internal/vmname, internal/safefile, internal/landlock and internal/daemon use the standard library alone, and internal/proxy uses it with internal/daemon, internal/landlock, internal/redact, internal/safefile and internal/vmname and nothing else. internal/devcontainer imports no module from outside devvm, but it uses internal/image, internal/jsonc, internal/msg and internal/shell.

internal/clithe command line. Each Cobra command has a file of its own, and its about holds its docs page, its help group and the reason it has no --json. The package also holds the run’s services (app.go), the argument and flag checks, whose failures are usage errors, help, --json, the CLI tests, docgen/, which writes the CLI reference, and doctor’s check of Linux’s pins (pins.go)

A --clone VM’s copy is cloneseed.go’s: its in-VM scripts initRepos, seedStage and seedApply, sent through the backend’s Exec, with the shallow file read through internal/safefile and the pack made by internal/hostgit’s git. Its uncommitted changes are cloneworktree.go’s seedTree: the index read through internal/safefile and normalised by internal/hostgit’s git, hostgit.DiffFiles for what differs, and each working copy read through a safefile.Root, opening each folder from its parent with OpenDir, so no link on the way is followed, then the record of what went, which clonecheck.go reads back. The settings and hooks are cloneconfig.go’s seedConfig, an allowlist of config keys whose URLs cleanURL takes the credentials out of, and a VM’s stash entry is saved by clonesave.go, without its untracked files. Tools.update is the step devvm tools update takes, which devvm update takes first, and filePorts works out a VM’s ports again from its devcontainer.json’s, with the rules of devvm ports add and devvm ports rm (reading the devcontainer.json again). vm.AgentImport reads each agent’s folder through that folder as an os.Root (links out of an agent’s folder). Launch.buildTools builds the tool images that a VM’s shared tools need and the share lacks, and retainTools is retention’s tools.unused-age. Inventory.GitKeeper names the VM that keeps a path locked, and cloneState is the script that reads a --clone VM’s state back, its stash entries included. A Git LFS object file is opened beneath the common dir through an os.Root, each folder on the way checked first, because an os.Root still follows a link that stays inside it. confinementFor chooses a start’s confinement from the tier, starter.start registers the interrupt’s cleanup around the backend’s Start, vm.Env.Terminal gives an agent’s login the terminal’s files (ui.Terminal), and AgentLogin.endLogin ends the login in the VM
internal/shellquoting for a POSIX shell (Quote, QuoteJoin), a word on one line for bash (QuoteLine, ANSI-C quoting) and a shell variable’s names (EnvName), with the standard library alone
internal/vmnamethe name of every machine devvm runs on a backend, VM, which a field or a parameter holds instead of a string, and the parsers that make one where it’s read. Parse reads a project VM’s name from an argument or a file name, and it also reads vm.json’s name and runs in project.Nth. ParseListed reads one that a backend lists. VM’s UnmarshalText reads one in a JSON file, which may be any machine’s, so a field that must hold a project VM’s is still checked with IsProject. Image names an image’s machine, and VM.Aside a remake’s old one. msg.M.VM reads back the VM a message’s function took. It also holds a project VM’s name grammar (Prefix, HashLen, IsVM, and VM’s IsProject, Hash, Slug, Short, ImageKey and a remake’s Aside), with the standard library alone, so the proxy uses it too (the checks on owners)
internal/projecta project folder: its VM’s name, the hash that names its VM’s state folder (project.Hash), its link targets, the folders that aren’t safe to use and its parents
internal/gitprotect.git protection: one scan for each check, a Locker for each host, which is Flags on macOS, Binds on Linux, whose pins the start sets, or else Watch, and the table of its reports. A nested repo is left to another only when that repo’s scan locks its git folder whole (snapshot.covered). gitprotect.Protector.Check is the check of a stopped VM, and for a VM that devvm 0.1.0 or 0.1.1-rc.1 made strict, the converter’s unstrict then takes diff.ignoreSubmodules = all out of its repos’ configs, on a context that an interrupt doesn’t cancel (context.WithoutCancel), and strictLeft does the same for devvm git-protect on and off and devvm rm, without the warning. gitprotect.Keeps says whether another VM’s protection still covers a path. The configs it reads, the watch’s hashed files and git’s .git, commondir and gitdir files all go through internal/safefile (.git protection)
internal/hostsafetythe folder’s other checks on the host: one Walk once the VM is stopped, which skips .git and finds set-id files and nested repos (hostsafety.Walk, which only starter.walk calls), git’s own test for a bare repo’s shape (hostsafety.IsGitDir), doctor’s read of safe.bareRepository (hostsafety.BareExplicit), and an SSH origin
internal/hostgitevery git command devvm runs on the host, with no fsmonitor, hooks, filters or signing programs, ssh only, none of the environment’s GIT_* variables and no prompts, and with GIT_NO_REPLACE_OBJECTS=1 and GIT_GRAFT_FILE=/dev/null, so it sees a repo’s real history. hostgit.UserConfig reads one key of git’s global and system config by the files’ names, the files that GIT_CONFIG_GLOBAL and GIT_CONFIG_SYSTEM name included
internal/sshconfigthe ssh config that reaches running VMs by name, and its Include line in ~/.ssh/config
internal/sshagenteach VM’s choice of SSH agent, devvm’s own agent and its keys
internal/buildbuilding and rebuilding images, and their records. build.Names checks an image name’s layers and refuses a shared tool’s name
internal/imageimage keys and names, with no side effects, and the shared tools’ registry, SharedTools: one entry for each toolchain, with its members, its detection, its installer, its guest environment, its PATH folders and its version files (the structure test’s names), and whether it’s built for glibc alone (image.ToolDef.GlibcOnly)
internal/fetchevery HTTP client, with the standard library alone: NewClient, with a timeout and HTTPSOnly or SameScheme, Retry and Transient, ReadCapped, Get, Resolve, which finds where a HEAD’s redirects end, and Download, which checks the SHA-256 and caps the size. fetch.Client.Trust adds your CAs to a client’s roots, for the download of devvm’s own mise and an agent’s OAuth refresh
internal/upgradedevvm upgrade: how this devvm was installed (Detect), the releases (Source, with the newest, Check for a notice, and Fetch, which checks minisign’s ED signature by the built-in key, then the SHA-256), the unpack, the link’s switch and its rollback, and Homebrew. upgradetest/, for tests only, has a TLS release server and a minisign signer
internal/from--from: references, registry digests with an anonymous token, Docker’s IDs and the recorded digests
internal/redactpasswords out of logs, with the standard library alone, and Secret, the type of the values that let whoever holds them act as you or as a VM (Secrets in the code). String redacts the run log’s lines, taking out proxy keys and URL passwords. In redacts another program’s log as it grows, in place and keeping its length. It reads a line not yet ended again from its start when the line is within MatchMax of what an earlier look read, and otherwise from MatchMax back, starring what runs on to an @ there, and Look.Cut does the same after a rotation’s cut. Unended redacts a copy’s cut end
internal/vmlogevery log a VM can drive, except the proxy’s own. Limit is the rate and length of what a VM makes devvm’s background processes write. The port forwarder and the link session write through it, and the link session’s warnings take their turns from its Allow. Capped is a background process’s log, held to its cap as it appends, with Trim at its next start. KeepVM is what the VM’s proxy (through proxy.IO.KeepLogs) and a build run on the logs the backend writes as the VM runs (backend.Run.Logs), the serial consoles’ among them. It watches each log in a goroutine of its own, redacts what each one gained every second (redact.In), so a reboot in place can’t leave the proxy’s password there, and skips a log that hasn’t grown. Redact is Lima’s redaction at the end of a start. Each rotation copies the log’s end to its .1 file, redacting only what the last look didn’t reach and masking a secret cut at its end, and empties it with f.Truncate, counting a log by what it holds past the hole its writer left, as Lima’s programs write at their own offset. The consolidation pass

A review of a body of work, and the review before a release, look across the code for copies:

  • two parsers of one format
  • a path built outside internal/paths
  • a list of files kept beside the folder that holds them
  • a value encoded in a string
  • two messages that say one thing
  • a comment that says to keep two places in sync
  • a test that copies a constant

Each copy gets one of three outcomes: extend the owner, make one owner, or leave it. Leave it when the only shared helper would be the wrong one, because a copy costs less than the wrong helper, and wait for a third copy before making one. The pass is part of those reviews, not a step every change runs.

Secrets in the code

A value that lets whoever holds it act as you or as a VM is a redact.Secret, from the moment devvm reads it until the place it’s used. That covers a VM’s proxy password (netpolicy.Key, proxy.Config.Password, backend.Confinement.ProxyPassword) and a build proxy’s, a secret’s value (secrets.Store.Value, Get and Save, and what ui.UI.Secret reads), the company proxy’s password and the Proxy-Authorization the proxy sends it, the values the proxy caches for a VM’s bindings (proxy.Lookup), and an agent’s API keys and tokens once they leave its login file (agentlogin.File.Get and SetKey, and the tokens a capture or a refresh brings). Two such values stay strings, as where secret values live explains: the value on its way through platform.KeychainGet and KeychainSet, which secrets.Store makes a Secret at once, and devvm desktop’s VNC password, which you must see. A Secret prints as <redacted> with %v, %s, %q, %x, %#v and every other verb, so a log line, an error or a struct printed with %+v never shows it. Its value is behind a pointer, because fmt prints a value in an unexported field without calling its Format, and such a field then shows only an address. Two Secrets are equal with == only when they’re the same one, so compare their values with Reveal, or the structs that hold them with reflect.DeepEqual.

Reveal is the only way to the value, and forbidigo refuses every call to it except in tests. So each place that must use a value says why in a //nolint:forbidigo // <why> on that line. Those places are the proxy’s password check and the headers it puts values in, the store’s file and the Keychain, the VM’s proxy URL and a login’s file, its refresh and its claims. Anywhere else, pass the Secret on. testdata/lint/forbidigo.go keeps a call to Reveal that the rule must report. The structure test refuses a struct that embeds redact.Secret outside internal/redact, which would take on its methods, and an interface that declares Reveal() string, whose calls forbidigo wouldn’t see. It reads the source alone, so it doesn’t see a Secret embedded through another type or reached through reflection.

Encoding a Secret as JSON or as text is an error (redact.ErrEncode), never <redacted>, so a value written somewhere by accident fails at once rather than losing your login. A file that must hold the real value therefore writes it through its own wire type, a struct with the value as a string that only that file’s reader and writer use:

  • The proxy’s config, proxy.json, is configFile, with Config’s fields in Config’s order, so its bytes, and the Sum that decides whether a running VM’s proxy starts again, match what earlier releases wrote. TestConfigFile holds the two types together.
  • A VM’s key in vm.json is netpolicy.NetMade’s own MarshalJSON and UnmarshalJSON, through netMade.
  • A secret’s file without a Keychain is the value and a line’s end, which secrets.Store.save writes and saved reads.
  • A login’s file is the agent’s own format, read and written whole as a map so that fields devvm doesn’t know stay, and a key or token leaves the map through agentlogin’s token and goes into it through setToken.

To add a field that holds a secret, give it the type redact.Secret. If a struct with it is written to a file, add the field to that file’s wire type, and check that a frozen release’s files still read and write the same bytes: TestV010ProxyConfigs does it for proxy.json, TestFixtureVMStates for vm.json’s sections, TestFixtureStoreGet for a secret’s file on Linux, and TestFixtureAgentStore for the agents’ login files, which every read leaves as they were.

Changing the state layout

State files describes the layout, and the design note says why it’s built that way. Every path in it comes from internal/paths. paths.Dirs names the shared folders and files, and Dirs.VM(name) gives a VM’s paths.VM, whose methods name each file in the VM’s folder: Dirs.VMDir(hash), vms/<hash>/, for a project VM, and run/builds/<name>/ for a build VM. A new socket goes in Dirs.Run(), named by a hash, and TestSocketsFit checks the longest path against paths.SocketMax. A new record that only devvm writes is JSON, read with encoding/json, which ignores fields it doesn’t know, and written whole with state.WriteFile. A new default goes in internal/settings, which reads config.toml strictly and saves settings.json, and a new lock is an OS file lock (platform.LockFile and its kin) on a file that paths names.

The data folder and the config folder each hold a version file with their layout version, state.Layout in internal/state/layout.go. Before each command that reads them, state.CheckLayout takes version.lock in the data folder and compares both files with state.Layout. A folder without the file gets this devvm’s version, the same version goes on, and a newer one stops the command with layout_newer, because a newer devvm changed the folders. An older one runs the migrations from that version to this one, in order, and then writes state.Layout into both files. skipsLayout in internal/cli/root.go lists the commands that skip the check: help, completion, the version and devvm’s own hidden commands.

testdata/script/layout.txtar makes two VMs on the allowlist tier, a forwarded port, a link and a secret, lists every file and folder under the data and config folders, and compares the lists with the ones at the end of the script, one for macOS and one for Linux. A change to the layout, such as a new file, a renamed folder or a file that moves, changes a listing, so the test fails until you update it. When it does, decide whether the change needs a new layout version:

  1. A change that an older devvm would read wrongly, or a file that moves, raises state.Layout by one.
  2. It adds a state.Migration at the end of migrations(), which changes the folders from the version before to the new one. A migration takes paths.Dirs, and a run that it fails stops before the versions change, so the next run tries it again. TestMigrations checks that there’s one migration for each version before this one, and TestCheckLayout runs fake ones.
  3. It updates the listings in layout.txtar.

A new file that an older devvm doesn’t need to know about, or a field added to a JSON file, which an older devvm ignores, keeps the version and changes only the listings.

Released state

Someone who upgrades devvm keeps their VMs, defaults, agent store and secrets as the release they came from left them. Until 1.0, an upgrade from every release since 0.1.0 has to work. Each final release that changed what devvm writes on disk has a frozen copy of the state it left, called its fixture, and the tests run today’s devvm on every fixture, so a change that breaks an older release’s state fails the gate.

What a fixture holds

A release’s fixture is the folder testdata/v<release>/. Its darwin/ folder holds the state that the release left on a Mac, and its linux/ folder the state it left on Linux. For 0.1.0, that’s four VMs’ states, its defaults, its agent store and logins, the stubs’ record of the VMs, and what its --json printed for them, and the folder’s README.md lists what each VM has. The release made these files itself. Its generate.sh checks out the release’s tag in a temporary folder and runs generate.txtar with that version’s own CLI test harness, then copies what the run left, with each file’s mode in modes, because git doesn’t keep modes.

A fixture is frozen. It’s generated once, from the release’s own binary, and never edited or generated again, so never run its generate.sh from a newer devvm and never change its files. A release whose state is the same as the one before it adds no fixture, and neither does a release candidate, such as 0.1.1-rc.1, because only a final release that changes the state gets one.

The tests on every fixture

The unit tests read every fixture’s files with today’s readers. stateFixtures in internal/vm/fixture_test.go lists each release’s expectations: its VMs, the version of their vm.json, its layout version, its clones of one repo, and functions that check its VMs, its defaults and its agent store. 0.1.0’s entry is v010Fixture in fixture_v010_test.go. TestFixtureVMStates, TestFixtureVMsRead, TestFixtureSettings, TestFixtureAgentStore and TestFixtureClonesReadAsOneRepo run once for each release and system, and they check that each field the release wrote reads and writes back unchanged. TestStateFixturesListed fails when a folder in testdata has no entry, or an entry has no folder. Two packages keep a table of their own for what only they read. In internal/proxy, fixtureBinaries records the SHA-256 of the binary that made each release’s state, which its proxy configs name, and TestFixtureBindings and TestFixtureProxyConfig read every release’s bindings files and proxy configs. In internal/secrets, storeFixtures names a secret that each release’s store on Linux keeps as a file, which TestFixtureStoreGet reads through a VM’s binding. TestV010Rules is a copy of 0.1.0’s own tests of the proxy’s rules, kept apart from today’s.

The CLI tests run today’s commands on each fixture. A release’s scripts are in testdata/script/, named fixture_v and the release’s version without its dots, such as fixture_v010.txtar, fixture_v010_clone.txtar and fixture_v010_network.txtar for 0.1.0. Each one puts the state into a sandbox with fixture v<release>, which moves it to the sandbox’s folder: the folder’s path, each VM’s name hash, its folder’s and .git’s identities and its backend’s place become what they are there, each host port, and each port that a VM or the defaults forward, becomes one of the sandbox’s own that nothing on this host listens on, and nothing else changes. The ports change because a launch that finds a VM’s port taken, by a program of yours or by another run of the tests, rightly chooses another one and edits the VM’s Lima config. It also warns that it can’t forward a port that a program has, such as a web server of yours on 3000. A script names a forwarded port by what it was, as $FIXTURE_PORT_3000. The script then runs today’s devvm on it. Each --json must have everything the release’s had (json_superset), the read-only commands must change no file, and a launch must start each VM as it is, without a Lima edit. The scripts stay separate for each release, because their checks name that release’s VMs and what each one has, and TestFixtureScripts in internal/cli fails when a fixture has no script or a script names a fixture that isn’t there.

Changing what devvm does with state

A change that reads or writes state, such as a new command, a new section in vm.json or a new field in a record, runs its new commands on every fixture in the same commit, and reading the files isn’t enough. Add the steps to each release’s scripts, as fixture_v010_network.txtar runs rules by method and path on 0.1.0’s app VM and fixture_v010_clone.txtar runs devvm clone add on its web VM. When a fixture’s test fails, today’s devvm breaks the state that the release’s users have. Fix devvm, or add a migration, but never change the fixture.

A change in what devvm does with existing state gets a line in CHANGELOG.md, in the Unreleased section at the bottom until its release moves it to the top: a step in What to do when the user has to act on it, and otherwise a line in the group of the people who notice it, as Releasing says. When the user has to do something about it, such as run a command, devvm also tells them once, at the first launch after the upgrade.

Freezing a release’s state

At release time, after the tag exists, a final release that changed the state format gets its fixture. A release candidate gets none, even when it changed the state, and its final release’s fixture holds that state:

  1. Copy the newest fixture’s generate.sh, generate.txtar and README.md into testdata/v<release>/. Set the tag, the version and the script’s name in generate.sh, and add the VMs and commands to generate.txtar that make the state the release added.
  2. Run generate.sh on a Mac and on Linux, which writes darwin/ and linux/. 0.1.0’s were made on an arm64 Mac and on x86_64 Fedora.
  3. Add the release’s entries in stateFixtures, fixtureBinaries and storeFixtures, and its scripts, made from the newest release’s scripts with checks of its own VMs.
  4. Commit the folder as the run left it. The older fixtures stay as they are.

The support window

An upgrade from every release since 0.1.0 works until 1.0. When a release leaves the window, its fixture and the code that only its state needs, such as a reader of a field that only that release wrote, go together, in one commit that says which release left and why. The commit deletes testdata/v<release>/, its scripts and its entries in the tables above.
