# The structure test and owners

## The structure test

`internal/structure` parses every Go file in the repo, tests and every platform's included, generated files left out, and checks what linters don't. `mise run test` runs it. Each failure starts with its rule and the file and line:

| Rule | Checks |
| --- | --- |
| `max-methods` | no type has more than 24 methods, value and pointer receivers together, and no interface declares more than 24, not counting the interfaces it embeds; a larger one splits by what its methods do |
| `no-init` | no `func init()` |
| `package-vars` | a package-level `var` is a blank interface check, an `Err*`/`err*` sentinel from `errors.New` or `fmt.Errorf`, a `regexp.MustCompile`, `template.Must` or `sync.Once*` result, a `//go:embed` file, or listed in `allowedVars`; anything else becomes a field, a const or a local |
| `layers` | which packages import which, in non-test files (tests may wire packages together) |
| `owners` | in non-test files, only its owner runs a host command that `commands` lists, only the files `execSites` lists make a host command, only `guardOwner` asserts a backend package's type, only `envOwner` reads a `DEVVM_` variable, but the settings `envSettings` lists, only its file in `envOwners` reads `HOME`, only its owner's string literals hold a text that `literals` lists, only its owner's string literals are, whole, a name that `names` lists, only its owner's calls to package `strings` split or join on a separator that `separators` lists, only `pathsOwner` builds a path in devvm's data or config folder, and only its file in `callers` calls a function that `callers` lists ([details](#the-checks-on-owners)) |

The layers:

- Only `cmd/devvm` and `internal/cli` import `internal/ui`; only `internal/cli` imports `internal/vm`; only `cmd/devvm` imports `internal/cli`.
- `internal/backend/...` imports none of `internal/vm`, `build`, `tools`, `netpolicy`, `secrets`, `project`, `gitprotect`, `sshconfig`, `sshagent`, `trust` or `vmssh`, so the port forwarder and the link sessions stay devvm's on every backend.
- Only `internal/backend/registry` and `internal/cli` import a backend (`lima`); only tests import `backendtest` and `internal/stubtest` and the packages below it, which import only `internal/msg` and each other. The stubs' binary, `internal/stubtest/stub`, and its state, `internal/stubtest/stubstate`, import nothing else of devvm's, because the binary stands in for the tools devvm runs and is built apart from it.
- `internal/proxy` imports no other devvm package but `internal/daemon` and `internal/safefile`.
- `assets`, `locales`, `internal/platform`, `internal/msg/gen`, `internal/testbuild`, `internal/hostgit`, `internal/shell`, `internal/vmname`, `internal/daemon`, `internal/fetch`, `internal/jsonc`, `internal/redact`, `internal/agents` and `internal/safefile` import no devvm package; `internal/agentlogin` only `internal/agents`, `internal/fetch`, `internal/jsonc`, `internal/proxy`, `internal/safefile` and `internal/state`, because it holds agents' logins; `internal/msg` only `locales`; `internal/paths` only `internal/msg`; `internal/state` only `internal/msg`, `internal/paths`, `internal/platform` and `internal/vmname`; `internal/image` only `assets`, `internal/agents`, `internal/msg`, `internal/paths` and `internal/shell`; `internal/devcontainer` only `internal/image`, `internal/jsonc`, `internal/msg` and `internal/shell`.

Everything it holds the code to is in `devvm()` in `internal/structure/structure_test.go`:

- **`largeTypes`** lists the types allowed more methods, which are `paths.Dirs` and `ui.UI`, each with its count as its maximum and why. A backend isn't one of them, because its methods are split by `backend.Backend`'s roles ([how a backend plugs in](extending.md#how-a-backend-plugs-in)). One that grows fails; one that shrinks fails until its maximum is lowered.
- **`allowedVars`** lists the other package-level vars, by package folder and name, each with why: values set by `-ldflags`, fixed tables, test fixtures. An entry whose var is gone fails.
- **`layers`** is the layering table: a layer's packages (`from`, but not `exceptFrom`) import none of `to` (but `exceptTo`); `x/...` is `x` and the packages below it.
- **`commands`** maps a host command to the one package that runs it. **`execSites`** lists the files that make a host command with `exec.Command` or `exec.CommandContext`, each with why, and a listed file that no longer makes one fails. **`guardOwner`** names `internal/backend/guard.go`, the one file that asserts a backend's type. **`envOwner`** names the one file that reads devvm's `DEVVM_` variables. **`envSettings`** lists the variables read elsewhere, each with the files that read it and why. A listed file that no longer reads its variable fails. **`envOwners`** maps another variable to the one file that reads it, which for `HOME` is `internal/paths/dirs.go`.
- **`literals`** maps a text that only one package's string literals may hold to that package and what the others use instead. **`names`** maps a name that only one package's string literals may be, whole, to that package and what the others use, and **`namesFree`** lists the folders whose literals may be one anyway: `internal/stubtest`, whose stubs are named after the commands they stand in for.
- **`callers`** maps a function to the one file outside its package that calls it, and a listed file that no longer calls it fails. A method is listed as `pkg.Type.Name`, such as `internal/paths.Dirs.AgentSettings`, and any call of a method by that name outside its package counts, because the check reads no types, so a listed method's name is its type's alone.

`TestRulesFail` breaks each rule, and each layer, on small sources and checks the failure names it.

Shell scripts that live in Go strings get shellcheck too, since lint's shellcheck only finds files with a shebang. `TestEmbeddedScripts` in `internal/structure` finds every call site that runs a script as `sh -c`, `/bin/sh -c` or `bash -c` (or `-lc`), in a `[]string` literal or a call's arguments, outside tests and the stubs. When the script is a constant, a literal, or a sum of them, such as `seedApply` with `seedMarker` in it, the test writes it to a file and runs `shellcheck -s sh` or `-s bash`, as its shell reads it, at `-S warning`, skipping when shellcheck isn't installed. A script built at run time can't be read there, so the test fails on one until `dynamicScripts` lists its file and expression with why: a fixed command around quoted paths, a devcontainer's own command, or a builder that a test of its package checks, as `internal/vm`'s `TestBuiltScriptsShellcheck` does for the scripts built from the agents' registry. A listed site that's gone fails too, so the list stays current. A shell given any other flag, such as `sh -ec` or `sh -e -c`, fails as well, because the test would miss its script: put options such as `set -e` in the script instead. `-s`, for a script on standard input, is fine.

## One owner for each concern

Each concern in devvm has one owner, the package or function that does it, such as `internal/hostgit` for every git command devvm runs on the host, `internal/paths` for every folder and file devvm uses, `internal/settings` for every default (`settings.Read` and `settings.Save`, over `config.toml` and `settings.json`, with each value's parser), and `locales/en.toml` for every message. Before you add a helper, a parser, a path, a file reader, a message or a table, find its owner and extend it. A second copy drifts from the first, and then one of them is wrong. [The packages](#the-packages) says what each package owns, and the failures of the checks below name the owners too.

### The packages

Each package owns these concerns, and a package's `doc.go`, where it has one, maps the package itself. `internal/fetch`, `internal/redact`, `internal/agents`, `internal/jsonc`, `internal/shell`, `internal/vmname`, `internal/safefile` and `internal/daemon` use the standard library alone, and `internal/proxy` uses it with `internal/daemon` and `internal/safefile` and nothing else. `internal/devcontainer` imports no module from outside devvm, but it uses `internal/image`, `internal/jsonc`, `internal/msg` and `internal/shell`.

### The checks on owners

An owner gets a check only when a second copy would be a bug or a security hole, and only when the check is exact, so that it never fails on code that's right. Each check's failure names the owner. The table is written from `ownerDocs` in `internal/structure/owners_doc_test.go`, which `TestOwnersDoc` checks it against and `TestOwnersAgree` checks against the structure test's own tables, so a change to a check changes its row there, and `go test ./internal/structure -run TestOwnersDoc -update` writes the table again:

<!-- The table is generated from ownerDocs in internal/structure/owners_doc_test.go: go test ./internal/structure -run TestOwnersDoc -update -->

| Check | Owner | Allowed elsewhere |
| --- | --- | --- |
| forbidigo, `testbuild.On` | `internal/cli`, whose `readOverrides` is the only code that asks whether this is a test build | nowhere: other packages take the overrides as fields |
| forbidigo, `os.FindProcess`, `syscall.Kill`, `unix.Kill` and `os.Process`'s `Kill` and `Signal` | `internal/daemon`, which signals a background process only while its pid file and its arguments say it's still that process (`Proc`), or through the process it started (`Handle`) | `internal/platform`; tests, which signal the children they started; and a child that hasn't been waited for yet, whose pid is still its own, with a `nolint` saying so |
| forbidigo, `unicode.IsGraphic`, `IsPrint`, `IsControl` and `Bidi_Control` | `msg.Safe` in `internal/msg/safe.go`, the one rule for which characters reach the terminal, which `msg.Printable`, `msg.OneLine`, the UI's renderers and devvm agent save's diff follow, so a second rule can't let through what this one refuses ([Colors](cli.md#colors) says what it refuses) | a check that isn't about the terminal, such as a path one line long, with a `//nolint:forbidigo` saying so |
| forbidigo, HTTP clients | `internal/fetch`, whose `NewClient` sets each client's timeout and redirect policy (`HTTPSOnly` or `SameScheme`), and whose `Retry`, `Transient`, `ReadCapped`, `Get`, `Resolve` and `Download` try again after the failures that may pass, cap what a body or a download may hold, follow a HEAD's redirects to where they end and check a download's SHA-256 before anything uses it. `fetch.Client` is its own type, so a client that `NewClient` didn't make, such as `&fetch.Client{}`, fails every request, and a caller changes a client's transport through its `Transport` method | `internal/proxy`, which is the standard library only, and tests, which make their own servers' clients |
| forbidigo, `netip.Addr`'s `IsPrivate` | `proxy.Public` in `internal/proxy/proxy.go`, the one judge of whether an address is on the internet: netip's classes, the table of the other ranges that aren't (`notPublic`), and the IPv4 address in a NAT64 or 6to4 address. | forbidigo, `os.Open`, `os.OpenFile`, `os.ReadFile`, `os.OpenRoot`, `os.OpenInRoot`, `os.DirFS` and `os.Root`'s `Open`, `OpenFile`, `ReadFile` and `FS`, in the code that reads files a VM can write or swap: `internal/gitprotect`, `internal/agentlogin`, `internal/vm`'s `devcontainer.go`, `detect.go`, `paste.go` and `agentsave*.go`, `internal/netpolicy/rules.go`, and `internal/proxy`'s `config.go` and `policy.go` | `internal/safefile`, which imports only the standard library, so the proxy reads with it too. Its `Read` and `Open` open a file without blocking and, unless the caller passes `Follow`, without following a symbolic link at the path's end. They then check the file they opened, not its name, so a FIFO, a device or a folder is refused with `ErrNotRegular`, a file past its cap with `ErrTooLong`, and, with `OneLink`, a file with another hard link with `ErrLinked`. A FIFO that the VM swaps in after a check can't hold devvm, and a link to `/dev/zero` can't flood it. `Checked` checks a file its caller opened another way in the same way, such as devvm paste's copied file, which `platform.OpenNoLinks` opens following no link but the system's, through `openat`, which the standard library doesn't have on macOS. `OpenRoot` opens beneath a folder through `os.Root`, never through a link out of it, and its `FS` lists and stats what's there but opens only regular files | every other file, which is devvm's own or the user's; tests, which make their own fixtures; and, with a `nolint` saying why, what opens a file to write it or a folder to lock it |
| forbidigo, `os.Setenv`, `os.Unsetenv`, `os.Clearenv` and `syscall`'s | each command's own environment, its `exec.Cmd`'s `Env`, because every command and background process devvm starts inherits devvm's. | the structure test's `owners`, host commands | the runners: the UI's `LoggedCmd`, which a package takes as a field and which runs a command into the run log, a backend's `Runner`, and `internal/hostgit`. A host command that one of them doesn't run is made only in the files `execSites` lists: those that make the command a runner then runs, such as Lima's `limactl` and mise's, and those whose command can't go into the run log, because it streams for as long as a link, the port forwarder or the desktop's relay lasts, asks on the terminal, outlives the run, or carries a secret | tests |
| the structure test's `owners`, a backend's other interfaces | `backend.As` in `internal/backend/guard.go`, because the registry's backends are behind its guard, whose type has only `backend.Backend`'s methods, so a type assertion to `backend.Forgetter` or `*lima.Lima` on one is always false | tests |
| the structure test's `owners`, git | `internal/hostgit`, which runs git without the repo's fsmonitor, hooks, filters or signing programs, over ssh only, without the environment's `GIT_*` variables, prompts, replace refs or grafts. It's also the only package whose string literals may be `"push"`, whole (`names`), and none is: a `--clone` VM's copy goes through the backend's `Exec` (`internal/vm/cloneseed.go`), never git's transport, whose receive-pack refuses shallow and SHA-256 repos. ### Agreement tests

When two places must agree but can't be one, a test checks that they agree. `TestEveryPartHasAPolicy` checks that every image part has its policy, `TestSharedToolsPolicies` that the policies in `assets/shared-tools/` are one for each shared tool in `image.SharedTools`, `TestConfigTools` that `assets/shared-tools/mise.toml` lists each shared tool's members and nothing else, `TestBuiltinPolicies` that every policy devvm ships parses, `TestEveryMessageIsUsed` that every message has a caller, `TestDocLinks` that every doc link is a message and a heading, `TestPreludeUsers` that only the scripts that get the prelude use it, `TestDefsComplete` that every coding agent has its `[tool_alias]` line and its row in the docs' Supported agents table, `TestProvidersComplete` that every provider in `agents.Providers` has its row in the docs' table of the API keys the proxy puts in, `TestToolchainsComplete` that every toolchain has files that call for it and its row and section on the toolchains page, which names those files and its `PATH` folders, `TestFormatsCoverLogins` that every agent's login file has its format in `internal/agentlogin`, and `TestReferenceIsCurrent` that the CLI reference matches the commands. A new pair of places that must agree gets such a test.

### The consolidation pass

A review of a body of work, and the review before a release, look across the code for copies:

- two parsers of one format
- a path built outside `internal/paths`
- a list of files kept beside the folder that holds them
- a value encoded in a string
- two messages that say one thing
- a comment that says to keep two places in sync
- a test that copies a constant

Each copy gets one of three outcomes: extend the owner, make one owner, or leave it. Leave it when the only shared helper would be the wrong one, because a copy costs less than the wrong helper, and wait for a third copy before making one. The pass is part of those reviews, not a step every change runs.

## Changing the state layout

[State files](../internals/overview.md#state-files) describes the layout, and [the design note](../internals/design.md#the-state-layout) says why it's built that way. Every path in it comes from `internal/paths`. `paths.Dirs` names the shared folders and files, and `Dirs.VM(name)` gives a VM's `paths.VM`, whose methods name each file in the VM's folder: `Dirs.VMDir(hash)`, `vms/<hash>/`, for a project VM, and `run/builds/<name>/` for a build VM. A new file of a VM's gets a method on `paths.VM`, so it lands in the VM's folder, and `vmFolders.teardown` in `internal/vm/teardown.go` deletes it with the folder, with no list of files to update. A new socket goes in `Dirs.Run()`, named by a hash, and `TestSocketsFit` checks the longest path against `paths.SocketMax`. A new record that only devvm writes is JSON, read with `encoding/json`, which ignores fields it doesn't know, and written whole with `state.WriteFile`. A new default goes in `internal/settings`, which reads `config.toml` strictly and saves `settings.json`, and a new lock is an OS file lock (`platform.LockFile` and its kin) on a file that `paths` names.

The data folder and the config folder each hold a `version` file with their layout version, `state.Layout` in `internal/state/layout.go`. Before each command that reads them, `state.CheckLayout` takes `version.lock` in the data folder and compares both files with `state.Layout`. A folder without the file gets this devvm's version, the same version goes on, and a newer one stops the command with `layout_newer`, because a newer devvm changed the folders. An older one runs the migrations from that version to this one, in order, and then writes `state.Layout` into both files. `skipsLayout` in `internal/cli/root.go` lists the commands that skip the check: help, completion, the version and devvm's own hidden commands.

`testdata/script/layout.txtar` makes two VMs on the allowlist tier, a forwarded port, a link and a secret, lists every file and folder under the data and config folders, and compares the lists with the ones at the end of the script, one for macOS and one for Linux. A change to the layout, such as a new file, a renamed folder or a file that moves, changes a listing, so the test fails until you update it. When it does, decide whether the change needs a new layout version:

1. A change that an older devvm would read wrongly, or a file that moves, raises `state.Layout` by one.
2. It adds a `state.Migration` at the end of `migrations()`, which changes the folders from the version before to the new one. A migration takes `paths.Dirs`, and a run that it fails stops before the versions change, so the next run tries it again. `TestMigrations` checks that there's one migration for each version before this one, and `TestCheckLayout` runs fake ones.
3. It updates the listings in `layout.txtar`.

A new file that an older devvm doesn't need to know about, or a field added to a JSON file, which an older devvm ignores, keeps the version and changes only the listings.

### Released state

Someone who upgrades devvm keeps their VMs, defaults, agent store and secrets as the release they came from left them. Until 1.0, an upgrade from every release since 0.1.0 has to work. Each final release that changed what devvm writes on disk has a frozen copy of the state it left, called its fixture, and the tests run today's devvm on every fixture, so a change that breaks an older release's state fails the gate.

#### What a fixture holds

A release's fixture is the folder `testdata/v<release>/`. Its `darwin/` folder holds the state that the release left on a Mac, and its `linux/` folder the state it left on Linux. For 0.1.0, that's four VMs' states, its defaults, its agent store and logins, the stubs' record of the VMs, and what its `--json` printed for them, and the folder's `README.md` lists what each VM has. The release made these files itself. Its `generate.sh` checks out the release's tag in a temporary folder and runs `generate.txtar` with that version's own CLI test harness, then copies what the run left, with each file's mode in `modes`, because git doesn't keep modes.

A fixture is frozen. It's generated once, from the release's own binary, and never edited or generated again, so never run its `generate.sh` from a newer devvm and never change its files. A release whose state is the same as the one before it adds no fixture, and neither does a release candidate, such as 0.1.1-rc.1, because only a final release that changes the state gets one.

#### The tests on every fixture

The unit tests read every fixture's files with today's readers. `stateFixtures` in `internal/vm/fixture_test.go` lists each release's expectations: its VMs, the version of their `vm.json`, its layout version, its clones of one repo, and functions that check its VMs, its defaults and its agent store. 0.1.0's entry is `v010Fixture` in `fixture_v010_test.go`. `TestFixtureVMStates`, `TestFixtureVMsRead`, `TestFixtureSettings`, `TestFixtureAgentStore` and `TestFixtureClonesReadAsOneRepo` run once for each release and system, and they check that each field the release wrote reads and writes back unchanged. `TestStateFixturesListed` fails when a folder in `testdata` has no entry, or an entry has no folder. Two packages keep a table of their own for what only they read. In `internal/proxy`, `fixtureBinaries` records the SHA-256 of the binary that made each release's state, which its proxy configs name, and `TestFixtureBindings` and `TestFixtureProxyConfig` read every release's bindings files and proxy configs. In `internal/secrets`, `storeFixtures` names a secret that each release's store on Linux keeps as a file, which `TestFixtureStoreGet` reads through a VM's binding. `TestV010Rules` is a copy of 0.1.0's own tests of the proxy's rules, kept apart from today's.

The CLI tests run today's commands on each fixture. A release's scripts are in `testdata/script/`, named `fixture_v` and the release's version without its dots, such as `fixture_v010.txtar`, `fixture_v010_clone.txtar` and `fixture_v010_network.txtar` for 0.1.0. Each one puts the state into a sandbox with `fixture v<release>`, which moves it to the sandbox's folder: the folder's path, each VM's name hash, its folder's and `.git`'s identities and its backend's place become what they are there, each host port becomes one that nothing on this host listens on, and nothing else changes. The ports change because a launch that finds a VM's port taken, by a program of yours or by another run of the tests, rightly chooses another one and edits the VM's Lima config. The script then runs today's devvm on it. Each `--json` must have everything the release's had (`json_superset`), the read-only commands must change no file, and a launch must start each VM as it is, without a Lima edit. The scripts stay separate for each release, because their checks name that release's VMs and what each one has, and `TestFixtureScripts` in `internal/cli` fails when a fixture has no script or a script names a fixture that isn't there.

#### Changing what devvm does with state

A change that reads or writes state, such as a new command, a new section in `vm.json` or a new field in a record, runs its new commands on every fixture in the same commit, and reading the files isn't enough. Add the steps to each release's scripts, as `fixture_v010_network.txtar` runs rules by method and path on 0.1.0's app VM and `fixture_v010_clone.txtar` runs devvm clone add on its web VM. When a fixture's test fails, today's devvm breaks the state that the release's users have. Fix devvm, or add a migration, but never change the fixture.

A change in what devvm does with existing state gets an entry marked Breaking in `CHANGELOG.md`, in the section for the release it goes out in. When the user has to do something about it, such as run a command, devvm also tells them once, at the first launch after the upgrade.

#### Freezing a release's state

At release time, after the tag exists, a final release that changed the state format gets its fixture. A release candidate gets none, even when it changed the state, and its final release's fixture holds that state:

1. Copy the newest fixture's `generate.sh`, `generate.txtar` and `README.md` into `testdata/v<release>/`. Set the tag, the version and the script's name in `generate.sh`, and add the VMs and commands to `generate.txtar` that make the state the release added.
2. Run `generate.sh` on a Mac and on Linux, which writes `darwin/` and `linux/`. 0.1.0's were made on an arm64 Mac and on x86_64 Fedora.
3. Add the release's entries in `stateFixtures`, `fixtureBinaries` and `storeFixtures`, and its scripts, made from the newest release's scripts with checks of its own VMs.
4. Commit the folder as the run left it. The older fixtures stay as they are.

#### The support window

An upgrade from every release since 0.1.0 works until 1.0. When a release leaves the window, its fixture and the code that only its state needs, such as a reader of a field that only that release wrote, go together, in one commit that says which release left and why. The commit deletes `testdata/v<release>/`, its scripts and its entries in the tables above.
