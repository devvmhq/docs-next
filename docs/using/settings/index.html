Using devvm
Settings and files

Settings and files

devvm writes nothing into your project folders. It keeps the settings you edit in ~/.config/devvm and everything it writes itself in ~/.local/share/devvm, and it reads a few environment variables. Your settings lists the files you edit, devvm’s data folder lists the ones devvm writes, and Overview explains how devvm keeps them.

Your settings

~/.config/devvm ($XDG_CONFIG_HOME/devvm) holds what you edit, and it’s the only folder of devvm’s that you should change by hand. devvm never rewrites a file of yours there. It reads config.toml and your own layers and CAs, it creates a new layer’s files when you run devvm layer new, it changes single lines of policy when you add or remove a rule for every VM, and it writes version when the folder has none and when it changes its folders to a newer layout.

FileWhat it holdsWritten by
config.tomlthe defaults that new VMs get and the retention settings, which win over what devvm’s commands save, the company proxy and an Ubuntu mirror (config.toml)you
policyyour network rules for every VMdevvm network allow -g, deny -g, rm -g, or you
layers/your own layers and their allowlistsdevvm layer new, then you
agents/your agents’ settings in devvm’s agent store, one folder for each agentdevvm agent import, devvm agent save, or you
ca/your company’s CA certificates, which VMs and builds trustyou
versionthe folder’s layout version, which says how devvm keeps its files heredevvm, when it’s missing or older

Edit the files in ~/.config/devvm, and never edit the ones in ~/.local/share/devvm. devvm writes those itself and rewrites them whole, so a change you make there can be lost, or can stop devvm from reading the file. To set a default by hand, put it in config.toml instead.

Upgrading devvm keeps this folder as it is. Back it up, such as in a dotfiles repo, to keep your settings and layers.

config.toml

~/.config/devvm/config.toml sets the defaults that new VMs get, the retention settings, the company proxy, an Ubuntu mirror, the release check, transparent mode and the API keys that VMs get as they are, in a file you write by hand. devvm reads it and never writes it. Every key is optional, and devvm has no config.toml until you write one. This example sets every key:

# The network tier new VMs get: open, internet, allowlist or none.
network = "allowlist"

# The ports new VMs forward: all, none, or ports and ranges.
ports = "5173,8000-8010"

# The features base gets, in the order they run, or [] for none.
features = ["cli-tools", "fzf", "omb"]

# The coding agents new VMs get, or [] for none.
agents = ["claude", "codex"]

# The layers new VMs get, bottom first, or [] for none.
layers = ["docker"]

# A mirror of Ubuntu's archive that base's first build tries first.
ubuntu-mirror = "http://mirror.example.com/ubuntu-ports"

# Whether a launch checks once a day for a newer devvm release.
release-check = true

# Whether confined VMs send tools that ignore the proxy settings to their proxy.
transparent-proxy = true

# The folder in every VM that devvm paste puts images and files in.
paste-dir = "/tmp/devvm-paste"

# New VMs' CPUs, and their memory and disk in GiB.
[size]
cpus = 4
memory = 8
disk = 100

# What devvm deletes on its own, with the keys devvm retention takes.
[retention]
logs.runs = 20
history.age = "90d"
history.count = 10
tools.unused-age = "30d"
orphans.age = "30d"
nix-cache.size = "20G"

# The company proxy, when the shell you run devvm in sets none.
[proxy]
https = "http://alice@proxy.example.com:8080"
http = "http://alice@proxy.example.com:8080"
no-proxy = "localhost,.example.com"

# Providers whose API keys an agent's VMs get as they are.
[pass-keys]
opencode = ["ollama"]
pi = ["ollama"]

Each key takes what its command takes:

KeyWhat it takes
networka tier, open, internet, allowlist or none, as devvm network -g sets it (choosing a tier), and never learn, because each VM learns the hosts it needs on its own
portsall, none or a list, as devvm ports -g takes it (size and ports)
featuresthe features that base gets
agentsthe coding agents that new VMs get
layersthe layers that new VMs get, bottom first
cpusa whole number, as devvm size -g takes it
memory, diska number of GiB, such as 8, 8.5 or "8G", as devvm size -g takes them
the [retention] keysthe retention settings, with a duration such as "90d" or a size such as "20G" in quotes, and a count as a number

The [proxy] table is the company proxy that every VM’s proxy, builds and devvm’s own downloads go through when the shell you run devvm in sets neither HTTPS_PROXY nor HTTP_PROXY, whatever the VM’s tier. No VM gets the company proxy’s settings itself. That shell’s settings win over the whole table. https and http take what HTTPS_PROXY and HTTP_PROXY take, an http:// URL or host:port, and no-proxy takes what NO_PROXY takes. A URL never holds a password, and devvm refuses one that does, so put only the user in it and save the password with devvm secret set proxy. No command saves the proxy, so it’s only ever in config.toml.

The [pass-keys] table names, for an agent, the providers whose API keys its VMs get as they are, which devvm otherwise keeps on this machine because the VM’s proxy can’t put them in, such as a local model server’s. Every VM with the agent gets a change at its next launch, and no command saves the table, so it’s only ever in config.toml. This is what it takes and refuses:

  • It takes opencode and pi, each with a list of the agent’s provider IDs as its auth.json names them, in lower case, such as ["ollama"] (opencode logins, pi logins).
  • devvm refuses another agent, a name that isn’t a provider’s ID and a repeat (config.toml names the line).
  • A provider whose key the VM’s proxy puts in (API keys the proxy puts in) never needs the table, because the proxy puts its key in without it. When the table lists one all the same, the VM gets that key’s placeholder from its next launch on, not the key, and devvm notes at each launch that you can take the provider out. A VM that got such a key as it was before then may still hold copies of it, which keep working, so make a new key when you don’t trust that VM (API keys the proxy puts in).

An Ubuntu mirror 

ubuntu-mirror = "http://mirror.example.com/ubuntu-ports"   # in ~/.config/devvm/config.toml

ubuntu-mirror is a mirror of Ubuntu’s archive, such as one your company or university runs, which the first build of base gets its packages from before it tries Ubuntu’s own. It must mirror the archive for this machine’s architecture: archive.ubuntu.com/ubuntu on an Intel or AMD machine, or ports.ubuntu.com/ubuntu-ports on an Apple silicon Mac or another arm64 machine. Give it as an http:// or https:// address without a user, a query or spaces, and devvm refuses anything else (config.toml names the line). A package that the mirror doesn’t have, or a mirror that doesn’t answer, falls back to Ubuntu’s archive for that file.

  • What it can’t do: a mirror can’t give base a package that Ubuntu didn’t publish, because apt and devvm both check every list and package against Ubuntu’s archive key. A mirror that’s behind can still serve old lists, and devvm refuses lists more than a day older than the Ubuntu cloud image base starts from, names the mirror and keeps none of the build’s packages (old package lists). A mirror that fell behind after that image’s date can still give base packages older than Ubuntu’s, so set only a mirror you trust to keep up (base’s packages).
  • What uses it: only the first build of each base, because a later build of the same base installs the packages devvm kept from that first build (base). VMs don’t use it, and neither do layers or a --from base.
  • Where it’s set: no command saves it, so it’s only ever in config.toml.

The paste folder

paste-dir is the folder in every VM that devvm paste puts images, PDFs and copied files in, /tmp/devvm-paste unless you set it. Each launch makes the folder in the VM when it’s missing, mode 700 and the VM’s user’s own. It leaves a folder that’s there as it is, so a folder of your own, such as /home/USER/pastes where USER is your user in the VM, keeps its mode and its other files. A launch warns, and goes on, when:

  • what’s at the path is a symbolic link, isn’t a folder or isn’t the VM’s user’s, and devvm paste then refuses the folder;
  • it can’t make the folder, as under a file.

It’s one fixed path for every VM so that you can allow it once in an agent’s settings. Give it as an absolute path without a trailing slash, made of letters, digits and ., _ and -, and devvm refuses anything else (config.toml names the line), because the path goes into a shell in the VM and onto your clipboard. A change applies to each VM at its next launch, which makes the new folder, and devvm paste uses the new folder at once. No command saves it, so it’s only ever in config.toml.

The release check

When you run devvm in a terminal, it checks at most once a day for a newer devvm release, and when one is out it says so in one line before it opens the VM, naming the release, the version you have and devvm upgrade. devvm never installs anything on its own, so you upgrade with devvm upgrade when you choose to. release-check = false turns the check off, and so does setting DEVVM_NO_RELEASE_CHECK=1 in the environment, as CI can. release-check must be true or false, and devvm refuses anything else (config.toml names the line). No command saves it, so it’s only ever in config.toml.

The check never announces a prerelease, unless Homebrew’s devvm-rc formula installed devvm, which follows prereleases and announces a newer prerelease or release, whichever is newest (trying a prerelease). It never makes devvm wait, and devvm doctor shows what it found last. devvm says nothing without a terminal, with --no-input, for a devvm built from its source, or for a copy that neither the install script nor Homebrew installed, which devvm upgrade can’t upgrade. The release check explains what the check reads and when its line shows a new release.

Transparent mode

On every tier but open, devvm sends a tool that ignores the proxy settings to the VM’s proxy by the names it looks up, which is transparent mode. It’s on unless you turn it off. transparent-proxy = false turns it off for every VM that has no setting of its own, and devvm network transparent on or off gives one VM its own, which comes first. A change applies at each VM’s next launch. transparent-proxy must be true or false, and devvm refuses anything else (config.toml names the line). No command saves it, so it’s only ever in config.toml.

Where a default comes from

For each default, devvm uses the first of these that sets it:

  1. A flag for one VM, such as --ports or --cpus.
  2. config.toml.
  3. What devvm’s commands saved: devvm setup, devvm size -g, devvm ports -g, devvm network -g and devvm retention save in ~/.local/share/devvm/settings.json.
  4. devvm’s own default.

A command that would save a default that config.toml sets refuses, names the file and the key, and changes nothing, because the value in config.toml would still win. To change that default, edit it in config.toml, or delete it there to let devvm’s commands set it again. In a terminal, devvm setup doesn’t ask about what config.toml sets, and it says so.

devvm size -g, devvm ports -g, devvm network -g and devvm retention show where each value came from, after a #. They show config.toml’s path for a value from config.toml, devvm: settings.json for one that a command saved, and devvm: default for devvm’s own:

$ devvm ports -g
5173,8000-8010 # /Users/you/.config/devvm/config.toml
$ devvm network -g
allowlist # devvm: default

With --json, the same commands add source, or sources for each value of devvm size -g and devvm retention, which is config.toml, settings.json or built-in.

When devvm can’t read it

devvm reads all of config.toml each time it needs a default, and it checks every key and value. A key it doesn’t know, such as a typo, a value that a key can’t take, and a file that isn’t TOML each stop the command, and devvm names the file and the line. Fix the line, and run the command again. config.toml has no key for the backend, because every new VM runs on Lima, so a backend key stops the command as an unknown key.

devvm setup

devvm setup chooses what new VMs get. In a terminal, it asks five questions, each starting from the current choice, and saves each answer in ~/.local/share/devvm/settings.json, as the command for that setting saves it. It skips a question that config.toml answers, saying so, and it refuses a flag that would change what config.toml sets.

  1. The features that base gets.
  2. The CPUs and memory that new VMs get, as devvm size -g saves them.
  3. The network tier that new VMs get, as devvm network -g saves it: open, internet, allowlist, which is the default, or none. Each new VM’s summary shows that tier, and when you customize the VM in a terminal, devvm asks for its tier, with Enter keeping the one the summary showed (what a new VM gets). --network TIER chooses for one VM and wins over the saved choice.
  4. The coding agents that new VMs get.
  5. The layers that new VMs get.
devvm setup                          # asks all five questions
devvm setup --features fzf,omb       # base's features, without asking
devvm setup --features none          # base gets no features
devvm setup --agents claude,codex    # new VMs' coding agents, without asking
devvm setup --layers docker          # new VMs' layers, without asking

devvm setup has three flags of its own, and each one chooses without asking anything. --features LIST chooses base’s features, as a comma-separated list or none for none, and devvm refuses an empty --features ''. --agents LIST chooses new VMs’ coding agents in the same way, and --layers LIST chooses new VMs’ layers. With any of the flags, what the flags leave out stays as it is. Without a terminal and without flags, devvm setup asks nothing and keeps base’s features, saving every feature when none was chosen yet. To change new VMs’ size without asking, use devvm size -g (choosing new VMs’ size), and to change their network tier, use devvm network -g (choosing a tier).

Coding agents for new VMs

The coding agents you choose in devvm setup are the ones a new VM gets unless you choose others for it. The summary devvm shows before it makes the VM names each of them as coming from devvm setup, and when you customize the VM, they’re checked in the list (what a new VM gets). --agents chooses others for one VM. The choice is for new VMs only, so a VM that exists keeps its agents, and devvm tools changes them.

devvm asks for them on its first run in a terminal, together with the size and base’s features, until you’ve chosen them. Until then, and when you choose none, new VMs get no agents by default. devvm setup --agents claude,codex and devvm setup --agents none choose them without asking, and devvm refuses a name that isn’t an agent’s, suggesting the closest.

Layers for new VMs

The layers you choose in devvm setup are the ones every new VM gets unless you choose others for it. They can be devvm’s built-in layers, desktop, docker and nix, and your own, which is how you give every new VM an extra of your own (extras of your own). The summary devvm shows before it makes a new VM names each of them as coming from devvm setup. When you customize the VM in a terminal, they’re already chosen under Layers in the list, and you can leave any of them out of that VM (what a new VM gets).

devvm setup --layers docker,desktop   # every new VM gets docker, with desktop on top
devvm setup --layers none             # new VMs get no layers
devvm --layers nix                    # this VM gets nix alone, not setup's layers
devvm --layers none                   # this VM gets no layers

devvm setup --layers takes the layers bottom first, in the order the image’s name joins them, so --layers docker,desktop gives new VMs the image docker+desktop. It refuses a name that isn’t a layer’s, suggesting the closest, and changes nothing. Until you choose some, new VMs get no layers by default, and devvm doesn’t ask for them on its first run. In a terminal, devvm setup asks for them last, after the coding agents. To set them by hand, use the layers key in config.toml, which devvm setup --layers then refuses to change.

  • --layers on devvm is the exact list of one VM’s layers, so it replaces setup’s layers, and --layers none makes a VM without any. A devcontainer.json’s layers go on top of setup’s (devcontainer.json).
  • The choice is for new VMs only. A VM that exists keeps the layers it was made with, and devvm setup says so when it saves the choice. To give that VM more layers, run devvm layer add in its folder (adding layers to a VM), and to take some out, devvm layer rm (taking layers out of a VM).

When a layer of yours that you chose in devvm setup has no script in ~/.config/devvm/layers, such as after you delete it, a new VM is made without it, and devvm warns, naming the layer. Run devvm setup --layers to choose the layers again. When the VM’s backend can’t run a layer you chose, such as docker on a backend without Docker’s engine, devvm makes no VM and names the layer. Then choose other layers for that VM with --layers, or change new VMs’ layers with devvm setup --layers.

Retention

devvm keeps what it makes until you delete it, and the retention settings tell it to delete some of it on its own. Every setting is off until you set it, so first run devvm space to see what each one would free: its RETAIN column shows each setting that’s on, beside the row it applies to, with what it would delete now (devvm space).

devvm space                                            # see what each setting would free
devvm retention                                        # show every setting
devvm retention history.age=90d tools.unused-age=30d   # set some
devvm retention history.age=off                        # turn one off
devvm gc --retention                                   # gc as usual, then apply them now

devvm retention shows every setting and its value, and off for each one that isn’t set. devvm retention KEY=VALUE... sets them, and devvm retention KEY=off turns one off, for example devvm retention history.age=90d tools.unused-age=30d. devvm refuses a key or value it doesn’t know, and a key with no value such as history.age=, and then it writes nothing. devvm saves the settings in ~/.local/share/devvm/settings.json. The [retention] table of config.toml sets them too, and a setting there wins over the saved one, so devvm retention refuses to change it. Each line that devvm retention shows ends with where its value came from, after a #. When devvm can’t read a file that sets them, it names the file, and the line for config.toml, and applies none of them.

KeyWhat devvm deletes
logs.runsthe run logs beyond the newest this many, which is 20 when it’s off
history.agethe exports of agents’ history written this long ago or more, such as 90d
history.countthe exports of agents’ history beyond the newest this many
tools.unused-agethe current shared tools that no VM has had for this long, counted from when devvm first found that no VM has them. While a VM is being made or is getting new shared tools, retention deletes none of them in that run, because that VM may not list the tools it picked yet, and it still applies the other settings
orphans.agewhat devvm keeps for VMs that their backend no longer has, once their state hasn’t changed for this long, as devvm gc --orphans does
nix-cache.sizethe shared Nix cache’s least recently used files, while it takes more than this, such as 20G; it’s 10 GiB when it’s off
ValueWritten asExamples
an agea duration, a whole number of minutes, hours, days or weeks30m, 12h, 30d or 2w
a sizea whole number of K, M, G or T, each 1024 of the one before, as devvm space shows them500M or 20G
  • When they apply: devvm applies the settings at the start of a command, at most once a day, except for orphans.age, which needs to ask each backend about its VMs, so only devvm gc --retention applies it. devvm gc --retention applies all of them at once. When two devvms start at once, only one of them applies the settings, and when it deletes something, devvm says what in one line.
  • The Nix cache’s size: the shared Nix cache also keeps to its size while VMs fill it, because a VM’s proxy deletes the cache’s least recently used files before a new file would take it past that size. A size you set applies to each VM from its next start.
  • What it never deletes: retention never deletes a VM, an image, a shared tool that any VM’s state lists, or anything in the backends’ own caches, which only devvm gc --caches frees. In cache/, the folder in devvm’s data folder that holds what devvm makes again when it needs it, retention deletes only the shared Nix cache’s files.

devvm retention –json

devvm retention --json prints the settings as one JSON object, as output for scripts describes. settings has every key with its value as you wrote it, and off for each one that isn’t set. sources has every key with where its value came from: config.toml, settings.json for one that devvm retention saved, or built-in for one that’s off. With --json the command only shows, so devvm refuses a KEY=VALUE with it.

{
  "version": 1,
  "settings": {
    "history.age": "90d",
    "history.count": "off",
    "logs.runs": "off",
    "nix-cache.size": "off",
    "orphans.age": "off",
    "tools.unused-age": "30d"
  },
  "sources": {
    "history.age": "config.toml",
    "history.count": "built-in",
    "logs.runs": "built-in",
    "nix-cache.size": "built-in",
    "orphans.age": "built-in",

A company’s CA

Some company networks inspect TLS through a proxy, such as Zscaler or Netskope, that shows its own certificates, signed by the company’s certificate authority (CA). This machine trusts that CA, but VMs and the VMs that devvm builds images in don’t, so their TLS connections fail. To make them trust it, put the CA’s certificate in ~/.config/devvm/ca:

mkdir -p ~/.config/devvm/ca
cp company-root.pem ~/.config/devvm/ca/

devvm reads every *.pem and *.crt file in that folder each time you open a VM, each time it builds an image and each time it resolves the shared tools’ versions, and it leaves other files alone. A file can hold one certificate or several, in PEM, the text form that starts with -----BEGIN CERTIFICATE-----. devvm accepts only CA certificates, and it sends only the certificates it read out of a file, never the rest of the file. It refuses the whole folder, naming the file, in these cases:

  • Anything else in a file, such as a private key, a certificate devvm can’t read or a certificate that isn’t a CA’s.
  • A link: a *.pem or *.crt file that is a link, or a folder that is one, because a link into a project folder would let that project’s VM replace the CA that every VM, build and proxy trusts. devvm doesn’t follow links there, so copy each certificate into the folder rather than linking to it.
  • A file it can’t read, or a folder it can’t read.

These trust the CAs:

  • Every project VM, in its system’s store, from its next launch.
  • Every build VM, for an image or for shared tools. devvm takes them out of a build VM before the image is finished, so images never keep them, and adding or removing a CA rebuilds nothing. A layer script of yours that copies the system’s CA bundle somewhere else does keep that copy (a company’s CA in builds).
  • The VM’s proxy, on every network tier, for the connections it makes itself, the refresh of a coding agent’s login included, which the proxy makes on this machine when the login is due, so a company proxy that inspects TLS doesn’t make the refresh fail.
  • devvm’s own mise, which devvm downloads once to resolve the shared tools’ versions on this machine. That download trusts these CAs as well as this machine’s own store, and on Linux so does that mise. On macOS, mise trusts them for most of its connections, but the part of it that checks where each tool’s release was built trusts only the CAs that macOS trusts, which Keychain Access shows. So on macOS, a company’s CA that mise needs has to be there too, where a Mac that your company manages usually has it already. When mise doesn’t trust a server’s certificate, devvm says so and names this folder.

devvm’s other connections from this machine, such as checking an image’s registry or Ubuntu’s image, trust this machine’s own store, as your other programs here do. When you take a certificate out of the folder, VMs stop trusting it at their next launch, and stores that copy the system’s CAs, such as Java’s cacerts, drop it too.

Most tools read the system’s store, among them apt, apk, curl, git and Python’s ssl module. For those that don’t, every VM’s environment points them at it:

A CA in the folder can read every TLS connection a VM makes, as it can this machine’s, so put only CAs there that you trust as much as this machine does. How it works › Network tiers explains how the CAs reach VMs, and Images and caching how builds use them.

devvm’s state

~/.local/share/devvm ($XDG_DATA_HOME/devvm) holds what devvm makes and keeps for you, and devvm writes everything in it, so don’t edit it by hand. It holds the defaults that devvm setup, devvm size -g, devvm ports -g, devvm network -g and devvm retention save in settings.json, below config.toml’s, and a folder for each VM in vms/, with the VM’s state, its own allowlist and its network logs. It also holds the images and the shared tools, the run logs, the agents’ history that devvm history export and devvm rm save, the ssh config for your VMs, and devvm’s own Lima home (lima/), where the Lima backend’s VMs and images live. devvm’s data folder lists each file and folder in it, with how each one is cleaned up.

  • On Linux hosts this folder also holds your secrets, in files under secrets/ that only you can read, so keep that in mind when you back it up. On macOS they’re in the Keychain.
  • devvm’s Lima home is its own, whatever LIMA_HOME says, so Lima settings meant for other VMs never reach devvm’s. Set DEVVM_LIMA_HOME to move it, for example to a sandbox or to a shorter path.
  • Only you can read devvm’s files, in either folder, because each time devvm runs, it makes both folders yours alone (devvm’s data folder). When devvm can’t read one of its files, it names the file and the line (a file devvm can’t read).

Project folders devvm refuses

A VM mounts its project folder read-write, so devvm refuses to make a VM for a folder that would give the VM more than the project. It refuses a folder that is or holds your home folder, ~/.config/devvm, ~/.local/share/devvm or devvm’s Lima home. It also refuses a folder inside one of devvm’s own folders, because a VM there could rewrite the scripts that every image build runs, or the files that devvm runs on this machine.

When devvm refuses a folder, make the VM in a project folder inside it, or keep the project somewhere else. A --clone VM mounts nothing from the folder, so devvm doesn’t refuse its folder.

Warning

If you mean to give the VM the whole folder, pass --unsafe-folder when you make the VM, and devvm warns you that the VM gets read-write access to it (only the project folder).

Colors

In a terminal, devvm colors the labels and links around its messages, while the messages’ own text stays in your terminal’s usual color. The tables that devvm ls, devvm images, devvm space and devvm doctor print are colored too, and their columns line up the same with colors or without:

WhatColor

devvm uses only your terminal’s 16 base colors, so your theme picks shades that read well on its background, light or dark. It never sets a background color.

devvm decides for standard output and standard error apart, and colors one only when it’s a terminal, so output you pipe or redirect to a file stays plain, tables included. What a command prints with --json is plain even in a terminal, and the run log is never colored. These environment variables change when devvm colors, and the first one that applies decides:

  • NO_COLOR, set to anything but an empty value, turns colors off.
  • FORCE_COLOR or CLICOLOR_FORCE, set to anything but 0, turns them on even when the output isn’t a terminal.
  • TERM=dumb turns them off.
