devvm 0.2.0

devvm 0.2.0

This page covers 0.2.0 and its release candidates, so far 0.2.0-rc.1, and it’s written as 0.2.0 is made, so each release candidate adds its changes here. 0.2.0-rc.1 adds to 0.1.1-rc.3, and 0.2.0 takes 0.1.1’s place, because its breaking changes need a new minor version. Install the release candidate with devvm upgrade --to 0.2.0-rc.1, the install script’s --version 0.2.0-rc.1, or brew install devvmhq/tap/devvm-rc, while Homebrew’s devvm stays on 0.1.0.

Each change below has a section of its own, which says what was wrong or missing, how it showed, how devvm works now and what you do. The changelog’s entry for each release gives each of the same changes in one sentence, sorted by who notices it, and its What to do section lists what to do once you’ve upgraded.

Breaking changes

At most 17 VMs run at once

Root in a VM could make the VM’s ssh port answer as a web server, and because that port is on localhost, a page it served could get the cookies of the apps you use on localhost, even in a VM that forwards no ports. Each VM’s ssh now uses one of the 17 ports from 1024 up that every browser refuses, so no page in your browser reaches a server in a VM through that port.

So at most 17 VMs run at once. A start past 17 fails and names the VMs that run on those ports, so stop one of them first (too many VMs at once).

A VM that forwards every port leaves out those 17 ports, so that a VM can’t take the ports that other VMs’ ssh needs. A server in the VM on one of them, such as an X server on 6000, reaches this machine only when you list its port with devvm ports, and devvm ports and each launch warn when a VM’s list names one of them (ports).

Each existing VM’s ssh moves to one of those ports at the VM’s next start. That’s the one change devvm makes to the VM’s Lima config, and like any change there, it gives the VM new ssh host keys. A VM that runs as you upgrade keeps its old port until then, and devvm warns of it at each launch, so run devvm stop in its folder, and its next start moves it.

Names are looked up as they’re written

The proxy used to look names up with this machine’s DNS search domain, which macOS takes from the network’s settings and Linux from /etc/resolv.conf. When either host had a public address, no rule judged the name that the search domain made, so with api.corp.example.com denied and ** allowing the rest, a VM could reach that host as api, or api.eu.corp.example.com as api.eu.

The proxy now looks each name up as it’s written, and it no longer adds this machine’s DNS search domain, so a short host name no longer reaches a host through the proxy. A tool in a VM that reached a host on your company’s network by a name such as jenkins now needs the host’s full name, such as jenkins.corp.example.com, and a block for a name without a dot says to use its full name (a name that doesn’t resolve).

Claude Code’s plugins in the agent store

devvm 0.1.0’s devvm agent import copied your whole ~/.claude/plugins into devvm’s agent store, where every VM with Claude Code could read it, plugins’ data included. The store now keeps only what a seed has of Claude Code’s plugins, as Claude Code’s plugins in a VM describes.

If you imported Claude Code’s settings with devvm 0.1.0, the first start of any VM takes your plugins’ data out of the store, along with the folder’s other entries that are this machine’s own, such as installed_plugins.json. It warns once, naming what it took, and it leaves your own ~/.claude/plugins as it is (Claude Code’s plugins).

If the store’s plugins folder is a link, or below one, which only a store you made yourself can be, no VM with Claude Code starts until you make it a folder of its own, because a VM’s mount would follow the link.

If a plugin’s data held a login of the plugin’s own, every VM with Claude Code could read that login, so sign in to that plugin again where you don’t trust those VMs. A VM that runs as you upgrade loses the store’s entries that are this machine’s own from its mount at the first start of any VM, so Claude Code there may not find the store’s plugins until that VM’s next launch. On a Linux host, the VM can keep seeing what it had read of them until its next start.

A linked agent store is refused

devvm agent import and devvm agent save used to write through a link in devvm’s agent store and take out whatever they hadn’t written in the folder it led to, which for a link to your home folder deleted your files.

Now they refuse a linked store: they fail before they change anything, naming the link, when a folder on the way to what they write in the store is a link, from ~/.config/devvm/agents down, such as ~/.config/devvm/agents/claude linked into a dotfiles repo. Make that folder one of its own, then run the command again (devvm’s agent store).

Changes

Each VM’s proxy runs as two processes

A VM’s proxy used to be one process, which read every byte the VM sent and held all of your secrets. It’s now two. Only devvm _proxy reads your Keychain, your agents’ login files and your other files, and devvm _proxy-child, which reads the VM’s network, asks devvm _proxy for the rest, such as each connection and each value bound to the VM.

So besides the VM’s own proxy password and CAs and your company proxy’s password, the code that reads every byte a VM sends holds only the values that the VM’s own bindings name, each for a few minutes after it was last asked for, and never a new login’s tokens, its refresh token among them (a VM’s proxy).

With the split, an error reply from an agent’s token endpoint reaches the VM as it is up to 1 MiB, and gets 502 past that, and a build’s proxy writes its logs to a logs/ folder of their own in its folder.

A VM’s proxy that runs as you upgrade stays one process, without a sandbox, until the VM’s next launch. That launch starts it again as two processes, because a launch starts a VM’s proxy again for every new devvm, and until then, devvm doctor names each VM whose proxy an older devvm started (the proxy runs without a sandbox).

The child’s sandbox on macOS

On macOS, devvm _proxy-child starts under sandbox-exec, with a profile that lets it write only its VM’s logs and the shared Nix cache and look at your policy files. A bug that a VM drove there couldn’t read your files, reach the Keychain or connect to this machine’s unix sockets, such as ssh’s and Docker’s (the proxy runs without a sandbox).

The child’s sandbox on Linux

On Linux, before it reads a byte of the VM’s, devvm _proxy-child confines itself with Landlock and a seccomp filter. A bug that a VM drove there could read and write only its VM’s logs and the shared Nix cache, and couldn’t change any other file’s mode, owner, attributes or times, run a program, or connect to a unix socket, such as an ssh master’s, Docker’s or your SSH agent’s. It could still learn whether a file of yours exists, its size and when it changed (the proxy runs without a sandbox).

A child without its whole sandbox

A proxy that can’t get its whole sandbox keeps the VM’s network, and devvm doctor warns. On macOS, if sandbox-exec is missing or fails to start the child, the child runs without the sandbox. On Linux, a kernel without Landlock or seccomp filters, or whose Landlock is older than ABI 6 or lacks its fix for signals between threads, confines the child only in part. Either way the VM keeps its network, and devvm doctor warns for each VM whose proxy runs that way, naming what the kernel lacks on Linux (the proxy runs without a sandbox).

The child connects only through devvm _proxy

Wherever its sandbox runs, a bug that a VM drove in the child can’t reach this machine’s services on localhost, such as your dev servers, Docker’s published ports and other VMs’ proxies, nor this machine’s own addresses or your LAN’s private addresses, unless a rule names the address, just as the VM can’t.

A rule such as devvm network allow 127.0.0.1:5432 still applies from the next connection, and a company proxy on localhost still works, though the child reaches whatever that company proxy reaches, as the VM does. Because devvm _proxy looks up the child’s names, the child reads no file below /etc on Linux and doesn’t talk to mDNSResponder on macOS (the child’s sandbox).

devvm doctor checks every VM’s state

devvm doctor warns once of each VM whose state devvm can’t read, naming the VM, the file and why, even when it can’t read the VM’s folder, and it changes nothing. It reads each VM’s vm.json as every command on a VM does. Such a VM used to hide doctor’s warnings about the other VMs’ policy files, and the warnings that devvm network gives for every VM, and it no longer does (a file devvm can’t read).

Credentials in a copied marketplace

A Claude Code marketplace can have a password or an access token in its clone’s git config or in its source in known_marketplaces.json, and every VM with Claude Code can read it once it’s in devvm’s agent store. devvm agent import and devvm agent save now warn when they copy such a marketplace. The warning names the marketplace, the store’s file and the keys, and the marketplace is copied as before (mounts).

devvm agent import’s bounds

devvm agent import copies at most 20,000 files, folders and links, 128 MiB, and 16 MiB in one file, of each agent’s folder. An agent’s folder that holds more, such as one that a VM’s project inside it filled, fails the import before the store changes, naming the folder, so take out what it doesn’t need and import again (importing from this machine).

A failed import changes nothing

A failed devvm agent import leaves the store as it was. That holds whether the import fails while it reads, such as at a file that changed meanwhile, or while it puts the settings and logins in place, such as at a login it can’t save. In the rare case that putting the store back fails too, the import names what it kept (importing from this machine).

A project in an agent’s folder

When a VM’s project folder is inside a coding agent’s folder on this machine, such as a skill you work on in ~/.claude/skills/mine, or holds one, such as ~/.pi, code in the VM can change that agent’s settings on this machine, and so the settings that devvm agent import copies for every VM.

Each launch of the VM now warns of it in one line, and so does the import, which also leaves out an agent’s folder that a link in a VM’s project folder leads elsewhere (project folders devvm refuses).

An import while a VM’s state can’t be read

devvm agent import can’t tell where a VM’s project folder is while it can’t read that VM’s state, so it follows no links then. It warns of each VM whose state it can’t read, naming the state. Until that’s fixed, it leaves out every link out of an agent’s folder, and an agent’s folder or login whose path leads through a link, one on the way to your home folder included unless only root can change it, so run devvm doctor and import again (importing from this machine).

Cursor’s CLI and your Cursor account

Cursor’s CLI in a VM can change less of your Cursor account. Its proxy refuses more of the methods that change your account, your team or your cloud agents, such as merging a cloud agent’s pull request, forking or pinning a cloud agent, or writing to its machine, and every call that the CLI itself makes still passes. Do those from Cursor on your machine (Cursor CLI login).

Pins

mise is 2026.11.10, in base and on this machine, the docker layer’s Docker is 29.10.0 and its compose 5.8.0, and Cursor’s CLI is 2026.11.17-f532c45. The new mise and Docker change what goes into the images, so base, every image built on it and every shared tool that mise installs are built again once.

Run devvm update in each existing VM’s folder. Until you do, a VM made from an older image says it’s outdated, and every existing VM says there are newer shared tools at the same versions. The first update or new VM builds base and each of its shared tools again, one at a time, which takes several minutes.

Status lines for slow steps

Some of devvm’s slow steps used to show nothing while they ran. In a terminal, devvm now shows a status line that says what it’s waiting for during these steps (a command fails):

  • finding the folder’s VM, checking it before a start, checking its network and reading its host keys, setting it up, running a devcontainer.json’s commands, looking up a folder’s disk, checking Lima, deleting a VM or an image, applying the retention settings and installing an upgrade
  • devvm ls reading the VMs, devvm doctor checking this machine, devvm agent import reading your agents’ folders and copying them into the store, and devvm agent save reading and comparing the VM’s settings
  • devvm clone add, clone fetch, clone on and clone off, devvm git-protect, devvm stop, a --clone VM’s check before devvm rm, a history export or import, and devvm ports as it starts a running VM’s port forwarder again
  • devvm link as it asks about the VMs its links lead to, link add, link rm, link publish and link unpublish, devvm group join and group leave, and devvm rm of a VM that others link to, as they give each running VM its changed links and check the VMs that links lead to
  • devvm network learn and network lock as they give a running VM’s proxy its new tier
  • every stop of a VM, as for devvm restart or a restart you agree to after changing a setting

Status lines while devvm waits

While devvm waits for another devvm that’s changing the same thing, such as a VM’s state, its folders’ layout, a group, an image’s build or the shared tools, a status line says so, and only while it waits. Some of those waits used to show nothing, and others printed a line after a few seconds that stayed. A run with -v, or with its output piped, no longer prints that line, because a status line shows only in a terminal without -v (a command fails).

Fixes

A project folder devvm can’t read

When you, or code in a VM that mounts it, took away your read permission on a project folder, devvm used to say that the folder’s VM was made for an earlier folder that was deleted or replaced, and offer devvm rm and devvm adopt. devvm now names the folder and why it can’t be read, so make it readable again (a folder made again).

Warnings and the status line

A warning used to be written onto the status line’s own line, and the status line’s next redraw could erase a question’s prompt and what you typed. A message that devvm prints during a slow step now prints above the status line, which comes back below it, and a question, the picker and an agent’s login in the VM take the status line away until they’re done (a command fails).

Claude Code’s setup-token login

devvm agent login claude --setup-token showed nothing and waited, as #57 reported. The login in the VM got no terminal, so claude setup-token, which draws full-screen, showed nothing. When devvm runs in a terminal, an agent’s login in the VM now gets a terminal of its own, as devvm’s shell does, so Claude Code shows the address to open and the prompt for its code. Without a terminal, --setup-token warns that the login may show nothing (Claude Code login).

Ctrl-C in an agent’s login

In a terminal, Ctrl-C now goes to the agent’s login in the VM and ends it, and devvm then says that the login ended or saved nothing. devvm puts the terminal back as it was before the login, even when a signal ends devvm itself (Claude Code login).

24-bit color in a VM

Programs in a VM, such as coding agents, fell back to fewer colors, as #54 reported, because devvm’s shell in a VM never got your terminal’s COLORTERM, and neither did an agent’s login or ssh to a VM by name.

devvm’s shell in a VM and an agent’s login with devvm agent login now get your terminal’s COLORTERM when it’s truecolor or 24bit, and no other value (opening a VM). The ssh config entries for reaching a VM by name now send it as your terminal has it, from the next time devvm launches or stops a VM, which writes them again. A VM made with --from gets it over ssh only when its image’s sshd accepts it (ssh access by name).

MCP servers’ logins

Claude Code keeps its logins to MCP servers in the VM’s ~/.claude/.credentials.json, the file where devvm puts the Claude login. Each launch and each devvm agent login claude used to write devvm’s copy of the login over the whole file, as #62 reported. So a login to an MCP server that you started with /mcp in a VM failed when devvm set the VM up again before it finished, such as when you ran devvm in its folder from another terminal, and one that finished was gone at the VM’s next launch.

With your subscription’s login, devvm now replaces only the Claude login in that file and keeps the rest, so the MCP servers’ logins you make in a VM stay in that VM, and they never reach this machine or another VM. With a Claude Code token, the VM’s file stays as it is (MCP servers’ logins).

Your claude.ai connectors

The connectors you added in claude.ai didn’t work in a VM, as #61 reported. The proxy put your subscription’s login only into requests to api.anthropic.com, so the connectors’ requests held the login’s placeholder and were refused.

With your subscription’s login, the VM’s proxy now also puts the login into requests to mcp-proxy.anthropic.com below /v1/mcp/, which carry the connectors’ traffic, from each VM’s next launch. So a VM with Claude Code can use every connector you added in claude.ai, as Claude Code on this machine can. A Claude Code token, from claude setup-token or in devvm’s environment, still goes only to api.anthropic.com (Claude Code login).

Code in the VM can now read and act through your connectors, so disconnect the ones you don’t want VMs to use, or deny mcp-proxy.anthropic.com with devvm network deny (your claude.ai connectors).

Claude Code’s plugins in a VM

Each VM’s ~/.claude/plugins used to be devvm’s agent store’s folder, mounted read-only, so whatever Claude Code writes there failed, such as a plugin’s data in ${CLAUDE_PLUGIN_DATA}, installing a plugin and updating a marketplace, as #56 reported.

Each VM’s ~/.claude/plugins is now its own folder, so all of those work. The store’s plugins are Claude Code’s read-only seed at ~/.claude/plugins-seed, so they load as before, a plugin keeps its data in the VM, and a plugin you install in a VM stays in that VM until devvm agent save copies it into the store. A store that devvm 0.1.0’s import filled keeps only what a seed has, as Claude Code’s plugins in the agent store says (Claude Code’s plugins).

Each VM gets its own ~/.claude/plugins at its next launch, without a restart, in place of its link to the store’s folder. Claude Code started in a shell that was open before that launch finds none of the store’s plugins, so start it in a new shell.

A project folder after your Mac restarts

After a restart, an unchanged folder could be on a device with another number, and devvm took it for another folder, as #60 reported. So every command on its VM refused it as made for an earlier folder at its path, a stopped VM’s start refused it as replaced, and the next check of .git called it replaced.

A folder at the same path, with no link on it and with the same inode and birth time, is now the same folder on whichever device it’s on. The VM’s next start records the folder on its new device before it mounts it, in the one change devvm makes to its Lima config. A folder that moved after a restart, before its VM started again, isn’t offered the VM, so devvm adopt VM moves it (one VM per folder).

A folder moved across a restart

devvm used to miss a folder that moved while a restart gave its disk another device number, and make it a second VM, and it called the gone folder of a VM whose disk was renumbered not connected. Each VM now records its folder’s volume, which no renumbering changes, so devvm finds such a folder. Once the VM has recorded its volume, devvm offers a moved folder its VM by its volume, inode and birth time, and calls a VM’s gone folder gone (a moved or renamed folder).

Each VM records its project folder’s volume at its first launch that finds the folder. Until then, a folder that moves while a restart gives its disk another device number still needs devvm adopt VM, and after a restart, the VM’s gone folder can still be called not connected. Both stay true for a VM whose folder was already gone before the upgrade, because it never records a volume.

A folder on another volume

A folder at the VM’s own path whose disk was renumbered, but on another volume than the one recorded, such as a copy of the disk with a volume ID of its own mounted there, is another folder, so devvm gives it the VM only after devvm adopt. On Linux, every launch checks the volume, so a Btrfs snapshot rolled back at the folder’s path, or the folder after you give its volume a new UUID, also needs devvm adopt (a folder made again). When devvm can’t read the volume at the launch after a renumbering, such as when diskutil doesn’t answer, each launch looks it up until it can (one VM per folder).

Two devvms at the agent store

Two devvms could write the agent store at once, so their files used to mix, or one could fail partway. devvm agent import, devvm agent save and a start that cleans Claude Code’s plugins out of the store now take turns, so a second one says it’s waiting and goes on once the first is done. A save that finds the store changed since it showed what differs now saves nothing instead of writing over an import (importing from this machine).

A failed save changes nothing

A save that failed partway, such as at a file it couldn’t write in one agent’s store or at the Claude Code login it saves last, used to leave the agents it had saved before the failure saved and the rest not. A failed devvm agent save now leaves the store as it was, because a save saves all or nothing, as an import does, and in the rare case that putting the store back fails too, it names what it kept. A file in the VM where the store has a folder, or the other way round, now fails the save before anything changes, naming the store’s path (saving a VM’s settings).

devvm agent save and a new Claude Code login

devvm agent save and a VM’s new Claude Code login take turns. While it saves Claude Code’s part of ~/.claude.json, the save holds the lock on Claude Code’s logins, the lock that a VM’s proxy holds while it saves a Claude Code login made in that VM. Ctrl-C while the save waits for either lock ends the wait (saving a VM’s settings).

Names that differ only in case

On a Mac, when the VM, or your home folder for devvm agent import, had a file whose name differed from the store’s only in case, such as foo.md where the store has Foo.md, devvm agent save and devvm agent import used to delete the store’s file and report success. They now treat such a file as one file, as macOS’s volume does, so the store’s file gets the new content and keeps its name, and the save’s diff shows it as changed.

Two names in the VM that differ only in case, such as A.md and a.md, would be one file in the store, so the save now saves nothing and names both, and so does an import of two such names from a home folder on a volume that tells case apart (saving a VM’s settings).

Names you choose in an agent’s settings

devvm used to take a plugin, a marketplace or an MCP server whose name had key, token, secret or passw in it, such as tokeneconomizer or secret-scanner, for a secret, as #55 reported. It put devvm-redacted in place of all its settings in the VM’s copy, so Claude Code refused the VM’s settings.json whole and every plugin was off in the VM.

devvm now knows the agents’ tables of names, such as Claude Code’s mcpServers, and judges only the fields under a name, so a server named secret-scanner keeps its command and still loses its env and its apiKey (keys in settings files).

If a VM’s copy of an agent’s settings file had devvm-redacted under a name you chose, such as a plugin’s marketplace, the VM’s next launch writes the whole copy over the VM’s own. Until then, devvm agent save leaves that file out and warns, so make any change to it in devvm’s agent store, or launch the VM again and make the change there.

Thanks to @jspiro for the report and @dhruv1220 for the tests’ idea in #58.

Folder names with separators in a row

devvm used to turn each character other than letters and digits in a folder’s name into its own dash, and Lima refuses a name with dashes in a row, so a folder named x--y, foo (copy) or C++ stuff got no VM, as #52 reported. devvm now turns each run of such characters into one dash, so those folders get a VM, and foo (copy) gets devvm-foo-copy-<hash>. The state that such a folder’s failed VM left is replaced when you run devvm there again (VM names). Thanks to @se6a for the report.

Host keys whatever a VM’s ports

When other programs on this machine, such as your own dev servers, held every port a VM lists, or the VM forwarded none with devvm ports none, a start that went no further than starting the VM, such as devvm clone fetch on a stopped --clone VM, used to leave the VM’s ssh host keys unpinned. devvm’s own ssh to the VM then failed until something else pinned them, so devvm clone fetch and devvm rm’s fetch failed with clone_fetch_failed.

devvm now pins a VM’s ssh host keys each time it starts the VM, whatever the VM forwards, and a command that finds the VM running without them pins them first (ssh into VMs).

A removed link’s connections

Removing a link with devvm link rm used to stop only the link’s new connections, so a target that never closed its end kept each open connection’s ssh process on this machine, and one of the 256 connections a client’s links carry at once, until the client or the target stopped. Removing a link now ends its open connections within a few seconds, and when a target starts again, the connections still open through its earlier start end as well (removing a link).

A settings file that’s one string

When an agent’s settings file in the VM was a single JSON string holding a placeholder, devvm agent save used to crash, and it now puts the saved value back in it. A login file on this machine that holds only null is now refused as not a JSON object, where saving a Codex or opencode login made in a VM failed on it (saving a VM’s settings).

Forwarded ports over IPv6

When this machine briefly couldn’t listen on a port’s IPv6 address, such as when it ran out of open files, the forwarder used to forward the port on 127.0.0.1 alone until the server in the VM restarted. So a client that connects only over IPv6, such as http://[::1]:PORT or a tool that doesn’t fall back to 127.0.0.1, didn’t reach the VM, and another program on this machine could take ::1 on that port and get those connections instead. The forwarder now tries the port again at the VM’s next report and forwards it on both addresses (when it can’t forward).

A forwarder after a burst

When the port forwarder ran out of open files while accepting a connection, it used to stop accepting connections on that port while it still listened there, so the port took connections that nothing answered until the server in the VM restarted. It now tries again shortly after, and so do a link’s socket and a browser login’s forward, which also carries at most 16 connections at once (how it reaches the VM).

Plain WebSockets

A plain ws:// WebSocket now connects through the proxy, where it used to get 502 (the proxy).

A pin that meets git’s rename on Linux

On Linux hosts, .git/config could seem to lose its pin. When git on this machine replaced .git/config just as devvm pinned it again, the pin used to fail, and devvm warned that the file lost its pin and couldn’t be pinned again, then that it was pinned again, at the VM’s next check, and a VM’s start could fail the same way. devvm now pins the file that the rename left, and warns only that it was pinned again (how a Linux host locks .git).

Stopped forwarders and link sessions

devvm stopping a VM’s port forwarder or link session, or a kill of either, used to leave its ssh connection to the VM running on this machine, with its control socket in devvm’s run folder. Each signal that devvm sends either one now also reaches what the process started, and either one stops its ssh before it exits. devvm gc --orphans also deletes a forwarder’s socket that nothing listens on (how devvm starts them).

Lookups with transparent mode off

In a VM confined to its proxy, with transparent mode off or stopped, a lookup through the system’s resolver on a Linux host used to wait out its timeout, because systemd-resolved’s stub kept retrying a name server where nothing listened, and workerd under wrangler dev waited about 40 seconds for each lookup.

The VM’s programs now ask the VM’s own name server, at 127.0.0.1, directly, from each VM’s next launch, so a lookup through the system’s resolver, such as getent’s or curl’s, fails at once, and so does workerd’s. A VM on the open tier keeps systemd-resolved’s stub (the VM’s resolver).

A Nix package downloaded twice

When two requests for a package that wasn’t in the shared Nix cache yet came close together, the second could download it again after the first had kept it, and the cache counted it twice against its cap. devvm now looks in the cache again before it downloads a package, so each package is downloaded once (the shared Nix cache).

A refused launch

When config.toml’s proxy named a user and no proxy secret was saved, devvm in the folder of a running VM used to refuse, as it should, but also stop the VM, and devvm restart stopped it before it refused. The same happened when your CAs folder couldn’t be used, or the VM’s CA or secret files couldn’t be readied.

On a launch or a devvm network change, devvm now checks the company proxy, your CAs, the VM’s CA and its secret files before it stops the VM’s proxy, and when it refuses, it says it left the VM and its proxy running as they were. devvm restart checks the company proxy and your CAs before it stops the VM (the proxy).

devvm desktop after a burst

When devvm desktop’s relay ran out of open files while accepting a viewer, devvm desktop used to end with an error, and the desktop’s port with it. The relay now tries again shortly, as the port forwarder does (the desktop relay).

A size that isn’t a number

When a VM’s state file held a size devvm couldn’t read as a number, such as "cpus": "four" after an edit by hand, the VM used to start with the image’s size without a word. devvm now refuses to start the VM or show its size, names the value, and says to set it again with devvm size. --cpus, --memory, --disk, config.toml and devvm size -g also refuse a number too big for devvm to read, which for a disk reached Lima as infinity (size).

Hardening

These fixes close ways that code in a VM, or a file it wrote, could reach past what devvm lets a VM do. Most of them change nothing you see.

devvm’s own folders in another case

On a Mac, where a name’s case doesn’t count, a project at ~/.Config/devvm/layers used to get a VM with read-write access to devvm’s settings and layer scripts, because devvm compared a project folder with your home folder and its own folders by name alone. It now compares them by the folders themselves as well, so it refuses that project as it refuses ~/.config/devvm/layers. A VM already made in such a folder still mounts it, so delete it with devvm rm there. devvm also refuses an SSH key in a folder that a VM mounts by a name in another case (project folders devvm refuses).

Passwords in Lima’s console logs

Lima’s boot scripts write the VM’s proxy settings, with the VM’s own proxy password, to the VM’s serial console, which Lima keeps in its console logs for the VM, serial.log, serialp.log or serialv.log in the VM’s folder in devvm’s Lima home. devvm used to take the passwords out of Lima’s ha.stderr.log only. Once the VM has started, devvm now replaces each password with as many * in Lima’s console log for the VM as well, as it does in ha.stderr.log (the run log).

A VM and its SSH agent

A VM that forwarded your agent or devvm’s own used to be able to remove every key from it with ssh-add -D, lock it with a password of its own with ssh-add -x, or add keys to it, and every VM that shares devvm’s agent lost it then, and with your own agent, so did you.

A VM now reaches its agent only through its proxy, which passes on listing keys, signing and binding a session to a host, and refuses everything else, so ssh-add in a VM can still list and use the keys, but not remove, lock or add them. An editor’s connection gets the same agent as devvm’s shell, the one the VM started with (the SSH agents).

A VM that forwards an SSH agent and runs as you upgrade keeps the agent as it was until its next start, so it can still remove, lock or add keys, and devvm warns of it each time it opens the VM or changes its links. Run devvm restart in its folder to give it the relay at once (agent forwarding).

Links inside an agent’s folder

devvm agent import used to copy a link inside an agent’s folder as the file it led to, wherever that file was in the folder, so a link in ~/.claude/skills or ~/.claude/plugins/cache could put your history, ~/.claude/.credentials.json or a plugin’s data into the store, where every VM with the agent reads it. It now copies such a link only when it leads to one of the settings the import copies, and leaves any other out with a warning that names where it leads (importing from this machine).

Your plugins’ data stays on this machine

devvm agent import used to copy all of ~/.claude/plugins into the store, so every VM with Claude Code got the data that your plugins keep on this machine, which can hold their own logins. From that folder, it now copies only the marketplaces, their records and the plugins’ cache, and devvm agent save copies only those from a VM (importing from this machine).

A history export’s names

devvm history import used to leave out the agents’ logins and the files that devvm’s setup writes by their names as the export wrote them, so an export that spelled one another way, such as .claude/./settings.json or .claude//plugins, got it into the VM’s home. It now refuses a name with a . or empty part, and once the export is unpacked, it deletes what it leaves out by its path (importing history).

Every host in one form

A few of devvm’s checks used to read a host in a way of their own. devvm secret set --host, an MCP server’s URL and a NO_PROXY entry took a name with a letter that isn’t plain ASCII, such as the Kelvin sign, which Unicode’s case folding turns into k, as the ASCII name it folds into. --from took a registry’s host with such a letter, or an address in brackets before a trailing dot such as [::1]., as one on the internet.

Every host is now read as the proxy reads it. The proxy refuses a host with such a letter, so now:

  • devvm secret set refuses it
  • an MCP server with one gets no secret
  • a NO_PROXY entry with one matches no host
  • --from doesn’t take such a registry as public
  • devvm network rm with it never removes the rule with the plain letter

The proxy also answers 400 to a host with brackets around anything but an IPv6 address, such as [evil.com]:443, and a partial clone’s warnings now read a remote’s host without its trailing dot, so they name example.com, not example.com., and a remote at localhost. gets the same warning as one at localhost (how the proxy reads a host).

Connections to the proxy on Linux hosts

Each connection that a VM confined to its proxy makes to the proxy starts a devvm process on a Linux host, and with no limit, a VM that opened connections without end could start thousands of them and fill the host with processes. devvm now carries at most 256 of a VM’s connections to its proxy at once, and answers any past that with 503 before it reaches the proxy. A VM that’s running when you upgrade has no limit until its next start (the QEMU wrapper).

A closed connection’s ssh process

When a VM never closed its end of a forwarded port’s or a link’s connection, that connection’s ssh process used to stay on this machine after the program here, or in the client, had closed its side, so a hostile VM could take all 256 connections that a forwarder or a client’s links carry at once. The ssh process now ends once its client has closed and the VM has sent nothing for 30 seconds. So a program that stops sending and waits more than 30 seconds for an answer to begin, such as nc -N in front of a slow query, has its connection cut (how it reaches the VM).

What a VM’s proxy holds

A VM’s proxy used to count only its tunnels toward its limit, keep idle connections open without end, keep a plain HTTP request running after its client had gone, and take 1 MiB of a request’s headers inside an intercepted tunnel, so a VM could make it hold more and more. It now:

  • holds at most 2048 of the VM’s connections of every kind at once, where one without the VM’s password doesn’t count, and has at most 2048 requests to hosts under way at once
  • closes a connection that waits 10 minutes for its next request, or that lacked the VM’s password
  • ends a plain HTTP request a minute after its client has stopped sending and nothing has come back
  • takes at most 64 KiB of headers everywhere, and carries at most 100 HTTP/2 requests at once in a tunnel
  • lets long downloads, WebSockets and slow streams go on as long as they last (the proxy)

A NO_PROXY address with a zone

An IPv6 address with a zone in your company proxy’s NO_PROXY, such as fe80::1%eth0, used to send that address past the company proxy without its zone, as #59 reported. Such an entry now matches nothing, as it does in Go’s HTTP clients (behind a company proxy).

A NO_PROXY entry’s port

The proxy used to read git.test:0 as git.test on every port, so it sent those hosts directly instead of through your company proxy, and it read git.test:080 or git.test:+80 as port 80, which Go’s clients don’t. An entry whose port no request has, such as git.test:0, or whose port isn’t in plain decimal, now matches no host, as one past 65535 already didn’t (through a company proxy).

A VM never runs without its proxy

A devvm network change could leave a VM running without its proxy. A change between internet, allowlist and none on a running VM is now refused before the VM’s tier changes, so its tier never says one thing while its proxy enforces another. A VM whose proxy doesn’t enforce the tier the VM has now, or whose proxy is stopped for new settings and then can’t start again, is still stopped, and a devvm network change now stops it in that case as well (the proxy).

A VM’s logs and their caps

Root in a VM could write to its serial console, /dev/hvc0, without end, and the console log grew until this machine’s disk was full, and so could Lima’s own logs for the VM until its next start. While a VM runs, its proxy now keeps the disk space that Lima’s console log for the VM and Lima’s own logs for the VM each take under 10 MiB, with a .1 file of up to 10 MiB more, and replaces the VM’s proxy password in them as they grow. A VM that’s running when you upgrade gets this once a devvm command starts its proxy again (Lima’s hostagent).

devvm’s other logs

devvm’s other logs are held to their caps as well:

  • The port forwarder’s and the link session’s logs now stay under 1 MiB while they run, not only from their next start, and a link’s warnings take turns with the session’s other lines.
  • The build proxy’s log stays under 10 MiB, as a VM’s proxy’s does.
  • A run writes at most 128 MiB to its run log, and the run logs take at most 256 MiB together, though devvm never deletes the newest or one that a running devvm still writes (the run log).

How deep a save goes

A chain of thousands of folders used to keep devvm agent save busy for a long time while it held the agent store’s lock. The save now has an import’s bounds on depth, so a VM that sends folders nested more than 128 deep, or a path of more than 4,096 bytes, gets nothing saved, as an import of such folders does (saving a VM’s settings).
